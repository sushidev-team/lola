# Lola Mobile — architecture and plan

## Decision

- **UI:** Capacitor 8 shell hosting the *existing* Svelte 5 + Tailwind v4 frontend, aliased out of `desktop/frontend/src/lib` — the same `theme.ts`, `StatusPill`, `SessionsTable`, `Button`, `confirm.svelte.ts`, `filters.ts`, `ansi.ts`.
- **Terminal:** `@xterm/xterm` + the WebGL addon — literally `LiveTerminal.svelte` — fed raw PTY bytes, with `internal/vtterm` (already in this repo) running daemon-side as a shadow emulator to produce resync frames on connect and reconnect.
- **Transport:** WSS over TLS 1.3 carrying a versioned envelope that wraps `protocol.Request`/`Response` **verbatim** into the daemon's existing `d.handle`.
- **The socket does not live in JavaScript.** A native Capacitor plugin, `LolaTransport` (Swift on iOS, Kotlin on Android), owns the TLS connection, the hardware-backed device key, the pairing proofs and the frame codec. The WebView receives decoded frames over the bridge and never sees key material.
- **Both platforms from one codebase from day one.** iOS leads by weeks, not by milestones.

The repository is six weeks old and 243 of its 256 human commits come from one person. It already carries roughly seven hundred lines of hand-maintained invariants in `CLAUDE.md` and exactly one hand-maintained mirror of the status vocabulary — `desktop/frontend/src/lib/theme.ts`, pinned against `internal/state` by an eighty-six-line regex test because there is no compiler in common between Go and TypeScript. Every architecture that introduces a new UI language introduces a second such mirror; the native proposal introduces a third and a fourth plus a bespoke `go/packages` codegen tool to keep them honest. That cost is paid by one maintainer, forever, and it buys a better terminal on one platform out of two — the native proposal concedes xterm.js-in-a-WebView on Android by its own plan, because there is no maintained permissively-licensed native Android terminal view and Termux's is GPL-3.0. Meanwhile the WebView route reuses the one screen this repo has already paid to debug: the alternate-screen wheel routing, the `\x1b\r` shift+enter encoding, the `linkHandler` → daemon `openURL` guard, the `document.fonts.ready` refit. Reuse wins on the UI. It does **not** win on the transport, and the plan below reflects that split.

**Rejected, briefly** (each gets a full paragraph at the end): Flutter, because its only mature terminal engine has had zero commits in twelve months and vendoring a dead VT parser is the worst possible fit for a solo maintainer. Native SwiftUI + Compose, because it pays for two languages, a codegen tool and four vocabulary mirrors and then ships the WebView terminal on Android anyway. gomobile as a shared core, because `protocol.go` alone declares more than twenty fields `gobind` cannot bind, so the only API that binds is `Send(string) (string, error)` — which is JSON over FFI, which is what the socket already gives us for free. React Native, because there is no native terminal there either and you end up hosting xterm.js in a WebView with React's complexity on top. Compose Multiplatform, because no terminal emulator exists for it at all. And the Wails 3 iOS/Android target **already scaffolded in `desktop/build/`** — the option that would share the most code of anything here — because it is pinned at `v3.0.0-alpha2.117` and its mobile support is alpha; it is the one rejection worth revisiting later, and nothing in the transport or pairing design changes if it is.

**Settled since drafting (2026-08-28).** Five of the open questions below were answered by the maintainer and are no longer open; the body above and below reflects the answers.

1. **The phone gets shell access** — agent panes, `-shell-N` and `-dev-N` tabs alike. `shell` stays a *named* capability so it can be revoked and so it appears in the device list, but it is granted at enrolment rather than withheld. The consequence is stated once and not softened: terminal write on a `-shell-N` tab is arbitrary code execution on the developer's Mac, with their `gh` token, SSH agent and login keychain in reach. That is accepted deliberately, and revocation (below) is the control.
2. **The phone does most of what the desktop does.** `control` and `destructive` are granted at enrolment too, so spawning a session, triggering a review, toggling dev and killing a session are all phone actions. `destructive` and `switchAgent` remain behind the plugin-enforced biometric gate (60 s validity, one action per success); `kill` with `force: true` remains unported. What is *not* ported is project and configuration handling — the project form, `[defaults]` inheritance, the group layout — which stays a desk job for the reasons already given under *Deliberately not ported*. Projects remain read-only cards with a poll toggle and a start-session action.
3. **One daemon is the v1 constraint.** The phone pairs with exactly one daemon. No daemon switcher, no daemon id in the push payload, no cross-daemon session-id disambiguation. A second daemon means a second pairing and the app shows the most recently paired one only.
4. **Loss is handled by revocation from the desktop, not by stingy defaults.** That is the deliberate trade behind (1) and (2): the device list with a one-tap "Disconnect" is therefore not an M2 nicety but the mitigation the capability defaults lean on, and it must be reachable in the desktop app without hunting. Revocation bumps the `epoch`, so a revoked device fails its next frame and every reconnect thereafter, whether or not the phone is reachable.
5. **No Android push.** M5 ships APNs only. FCM, its Google Cloud project and the `oauth2/google` dependency chain are dropped rather than deferred-with-intent. Android therefore has no wake path: it is a same-network, app-in-foreground client, and Doze will close its socket with the screen. Written down here so it is a known shape rather than a bug report.

## What the phone is for

**What "away from the Mac" actually means, and it is a smaller claim than it sounds.** The data path is the local network — the same WiFi, a VPN back into it, or the opt-in tailnet of M6 — and nothing else. **No relay is built, ever**, so a phone with no route to the daemon has no route to the daemon. Push is the one channel that reaches a phone anywhere, and by design it carries no readable content (see *Notifications*), so the honest description of the product is **same-network control plus anywhere-buzz with no detail**. A push tapped off-network must therefore open onto the last snapshot behind the same "as of 12m ago" banner M3 defines, with every mutating control disabled and one line naming the actual reason — "not on <daemon>'s network" — never a raw connect error, never a blank answer card, and never the pairing screen (which is what revocation looks like and must stay distinguishable from it). The motivating scenario below is the next room, downstairs, or the garden; the train is served only for an operator who has already chosen `tsnet` or a VPN, and the plan should not pretend otherwise.

Ranked by how much of the product each carries.

**1. Answer a parked agent.** The median lola failure is an autonomous agent blocked for twenty minutes on a yes/no while its human is two rooms away. `protocol.PaneData` is already precisely an answer card — `hasQuestion`, `prompt`, `choices[{key,label}]`, `freeForm` — and no GUI client renders it today; the desktop makes you type into the terminal. Three taps on a phone is the entire justification for this project. The affordance is gated on `inputReason`: `question` and `idle_notification` take prose or a choice key; `permission_prompt`, `dialog` and `quota_limited` are alertable but **not** prose-answerable, because typed prose is swallowed by a keypress-driven widget or answers a different question than the one on screen.

**2. Unblock a stalled agent.** Quota exhaustion and the fallback path already notify. Everything stalls until a human switches agent, and switching is one tap.

**3. Triage what broke.** `escalated` CI failures (the reaction engine has exhausted its retries, so it is now a person's problem), `changes_requested`, `merge_conflict`. Bare `ci_failed` is noise while the engine still retries.

**4. See the terminal.** Not to work in it — to answer the thing the answer card could not parse, to press Escape on a modal, to read what the agent actually said. This is the screen that decides whether the app is worth having and it is the biggest technical risk in the plan.

**5. Start work.** "Kick off ENG-412 while I'm out" via the ticket picker, an existing branch, or an open PR.

**6. Merge-ready sweep.** `approved` plus green checks, batched into a digest, never an interrupt.

**Deliberately not ported.** Config editing in every form: the project form is twelve fields with `[defaults]` inheritance semantics and an `Inherits` bitmap whose zero value means "fully explicit", the group layout is a fail-closed permutation check, and the folder picker wants a local checkout. None of that is a phone job, and `SaveProject`/`SetProjectLayout` are not even on the socket — they are Wails services. Projects appear as read-only cards with a poll toggle and a start-session action. The terminal grid wall is not ported: nine `capture-pane` snapshots at six points is unreadable at 390 logical pixels; the phone gets the list and the filter chips. The kanban board is not ported: five horizontally-swiped columns is worse than the five chips `state.KanbanColumns()` already defines. The doctor overlay, the update overlay, CLI installation and daemon binary-skew reporting are desk concerns. `kill` with `force: true` is not ported and is not portable — see the capability model. Neither is `stop`: a phone that stops the daemon severs the only link it has back.

## Daemon side: the remote listener

Six new leaf packages, in the repository's existing style — one concern each, stdlib-first, every external tool behind a `func(...)` seam so tests never touch tmux or the network.

| Package | Owns | External deps |
|---|---|---|
| `internal/pair` | QR payload encode/decode, transcript construction, SAS derivation, proof HMACs. Pure: no exec, no net, no filesystem. | none |
| `internal/devices` | `~/.lola/devices.json` — the paired-device registry, atomic temp+rename at 0600 exactly like `session.Store`, plus the capability tiers and the global `epoch`. | none |
| `internal/remote` | The TLS listener, SPKI pinning in both directions, the frame codec, per-device authorization, bounded dispatch, the audit line. | `coder/websocket` (already an indirect dependency via Wails) |
| `internal/panebus` | One `tmux attach` PTY per pane name, byte fan-out to N subscribers, a bounded per-pane ring for resume, and the `vtterm` shadow emulator that produces resync frames. | `internal/vtterm`, `internal/tmux`, `creack/pty` (both already present) |
| `internal/push` | APNs over HTTP/2 with a `.p8` ES256 token. Outbound only, iOS only. | stdlib |
| `internal/mdns` | `_lola._tcp` advertisement, off unless `[remote].advertise`. Strictly optional — the QR carries addresses. **Shipped early**; see below. | none (execs `dns-sd`) |

**Discovery shipped ahead of M6, and with no dependency at all.** The reason it moved is the one this plan already names at *Reachability*: from M2 through M5 a phone holds an address list frozen at pairing time, so a new DHCP lease or a laptop carried between home and office bricks the app with no named failure — that is a reconnect problem, not a pairing one, and it was worth fixing before Android. `internal/mdns` registers the service by exec'ing **`dns-sd`**, which every Mac ships and which is the interface to the mDNSResponder already running, so the daemon supervises one child process instead of taking a dependency: no library to vet, nothing for `make tidy` to fetch, and the same exec-seam shape this module already uses for tmux, git and gh. The cost is a long-lived child (a `dns-sd -R` registration lives exactly as long as its process) and no Linux path, which lola does not have anyway. The library evaluation below is kept because it is the decision to revisit if a responder is ever needed in-process: `grandcat/zeroconf` is not used — its last push was December 2023 and it carries fifty-two open issues — and `brutella/dnssd` was the only maintained pure-Go DNS-SD responder; if discovery ever needs to stop shelling out, that is where to start, and if neither is healthy then `advertise` stays off and the QR carries addresses, which is exactly why discovery was made an optimisation rather than a dependency. `golang.org/x/oauth2/google` was in an earlier draft of this table for FCM and is **gone**: dropping Android push (*Settled since drafting* (5)) removes it, and with it `cloud.google.com/go/compute/metadata` and `google.golang.org/api` — a transitive cost this module, with its eight direct dependencies and its stdlib-plus-exec-seams ethos, does not have to pay. APNs is plain stdlib HTTP/2. Note also that `make tidy` runs `GOPROXY=off` because deps are already pinned, so adding any of these is a deliberate network-enabled step in its own commit, not something that happens incidentally.

**Where it hangs off the daemon.** `Run` already does `ln, _ := claimSocket(sock); go d.serve(ctx, ln)`, and `serve` takes a plain `net.Listener`. The temptation is to write `go d.serve(ctx, tlsListener)` and be done. **Do not.** `d.serve` hands raw connections to `handleConn`, which speaks the unauthenticated newline-JSON vocabulary with no envelope, no device identity and no capability filter — that is a straight line from the LAN to `stop`, `kill --force` and `renameProject`. `internal/remote` gets a `Handle func(context.Context, protocol.Request) protocol.Response` seam instead, bound to `d.handle` in production and to a stub in tests. The raw socket vocabulary is unreachable from TCP by construction, not by review.

Two new daemon files, named after the existing `statusagentwire.go` / `reviewvisible.go` convention:

- `internal/daemon/remotewire.go` — the `Daemon` fields (`remote *remote.Server`, `devices *devices.Registry`, `panes *panebus.Bus`, and the `func(...)` seams they take), `startRemote`/`stopRemote`, the capability policy applied before `d.handle`, and the audit writer.
- `internal/daemon/pairwire.go` — the socket commands `pairBegin`, `pairStatus`, `pairConfirm`, `devices`, `revokeDevice`. These are socket commands, not desktop-app methods, and that is requirement 4 made structural: the daemon owns the pairing window, so `lola pair` works headless, the desktop's "+ connect app" button is an ordinary socket client, and closing the desktop app changes nothing about whether the phone can reach the daemon.

**The envelope versions; the payload does not.** A new type in `internal/protocol`:

```go
type Frame struct {
    V       int             `json:"v"`              // 1
    ID      string          `json:"id,omitempty"`   // request correlation
    Type    string          `json:"type"`           // req | resp | event | pty | sub | pair.*
    Cmd     string          `json:"cmd,omitempty"`
    Seq     uint64          `json:"seq,omitempty"`  // event/pty ordering, for resume
    Pane    string          `json:"pane,omitempty"`
    Payload json.RawMessage `json:"payload,omitempty"` // an existing Request or Response
}
```

`Payload` decodes into `protocol.Request` and the result goes to the same `d.handle` the unix socket calls. Zero handler duplication. That is a claim about *plumbing* and not about *authorization*: a command becomes remotely reachable only when it is named in a capability tier (see below), so adding a command to `d.handle` grants the phone exactly nothing until someone writes it down. The *envelope* has to be new for five reasons the code makes plain. `protocol.Request` has nowhere to put a device identity — every field is command payload. It has no version field anywhere; today's compatibility story is "a daemon predating a command answers `unknown cmd`", which `CLAUDE.md` already documents as a debugging trap and which is intolerable when an App-Store-versioned phone meets an arbitrary daemon. `handleConn` is strictly serial per connection, so a five-minute `openTicket` blocks every subsequent request on that connection — both existing clients dodge this by dialling one connection per request, and a multiplexing phone would deadlock itself without a correlation `ID`. There is no push at all, so the envelope needs a frame *type* for the daemon to emit deltas instead of the phone re-pulling 12.8 KB every two seconds. And `Cmd` is a flat allowlist with no risk metadata, so per-peer policy has nowhere to live.

**The compatibility window, stated so it is not rediscovered by a user.** A daemon accepts `V` in `[V_current-1, V_current]` and refuses anything else with a close code and a machine-readable reason. The app is versioned by the App Store and the daemon by `go install`, so both directions of skew are ordinary: on a refusal the app shows a named screen saying which side is behind and what to do about it ("update lola on <hostname>" / "update Lola from TestFlight"), never a connect error. Widening the window is a decision, not a default — `V` is cheap precisely because refusing it is loud.

**Config.** A `[remote]` block on `config.Config`, global, and therefore deliberately outside the `ProjectInherits` bitmap — an inherited listener makes no sense and the bitmap's zero value means "fully explicit", so adding a global key to it would be a category error.

```toml
[remote]
enabled = false          # DEFAULT OFF. Enabling this grants remote agent execution.
bind = "localhost"       # off | localhost | lan | all | <explicit addr>
port = 7717
advertise = false        # mDNS. An optimisation, never a dependency.
```

**`bind` must mean something precise, because its name will be read as a guarantee.** `localhost` is the value the README leads with — it is what a tunnel, an SSH forward or a tailnet wants, and it is the M1 default. `lan` binds only interfaces whose addresses are RFC1918/ULA/link-local **and** whose names are not in the excluded set (`utun*`, `tun*`, `tap*`, `bridge*`, `docker*`, `vmenet*`, `ap*`), so a VPN, an OrbStack bridge or a hotspot interface does not silently become a listener; the set of bound interfaces is logged at startup by name, because "which interfaces did it actually take" is otherwise unanswerable. `all` is the honest name for `0.0.0.0` and is never a default. Even so, `lan` on a laptop means *every network this machine ever joins*, conference SSID included — the README must say that sentence, not paraphrase it.

```toml
[remote.push]
enabled = false
apns_key_file = "~/.lola/apns.p8"   # a PATH, never the key
apns_key_id = ""
apns_team_id = ""
apns_topic = "dev.sushi.lola.mobile"
apns_env = "production"             # production | sandbox
fcm_service_account = ""            # a PATH
min_priority = "action"             # urgent | action | info
```

`enabled` defaults to **false**, and a daemon whose `devices.json` is empty opens no listener at all even when it is true. A default that binds every interface on every lola install is a posture regression this repository's ethos forbids, and none of the three source proposals stated the default explicitly. The README and `config.example.toml` must say in plain words what enabling this grants: **a paired phone can type arbitrary prose into an autonomous coding agent and tear down worktrees.** That is the honest description of the feature and an operator deserves to read it before flipping the key.

**Invariants the new packages must respect.**

*Shutdown, and the ORDER is the whole invariant.* `drainConnWork` sets `draining` and then does an **unbounded** `connWg.Wait()` — that group was built for bounded socket-initiated work (`pollOnce`, `tickets`, `fallback`), and a WebSocket a phone holds open for six hours is the opposite of bounded. Registering a live stream there naively hangs graceful shutdown until the phone happens to disconnect: the exact race the drain group exists to prevent, arrived at from the other side. So on cancel, **`remote.Server` goes first and finishes its own work**: it closes its listener (so `Accept` returns `net.ErrClosed` exactly as the unix path does), then closes every live WebSocket and every PTY bridge with code `4503`, and only once those goroutines have returned does `drainConnWork` observe an empty group. Live streams register with `beginConnWork()` / `connWg` and refuse new work the moment `beginConnWork` returns false — but the guarantee that the group *drains promptly* comes from the server closing them, not from the phone behaving. If that ordering ever becomes awkward to hold, the alternative is a separate wait group with its own deadline for long-lived streams; what is not acceptable is an unbounded `Wait()` on a connection a remote peer controls.

*Cancellability.* The pane fan-out and the event push loop are **read-only**, so they hang off the cancellable `d.shutdownCtx`, the same posture and the same justification as `interpretLoop` and `reviewLoop`. They must **not** be `context.WithoutCancel`: aborting a read costs a repaint, not state. The observer and reconcile loops keep their existing shielded posture; nothing here changes them.

*Exec seams.* `remote.Server` takes `Handle`, `Attach func(pane string, cols, rows int) (panebus.Sub, error)` and `Now func() time.Time`. `panebus` takes its tmux invocations as seams. Neither package's tests touch a socket or a process.

*Fail closed, everywhere.* An unknown envelope `V`, an unknown frame `Type`, a `Cmd` that is not in a capability tier (which is not the same as "a `Cmd` the daemon does not have" — see the closed allowlist below), a device absent from the registry, a device whose `epoch` is stale — refuse, log, close, mutate nothing. Never reach `d.handle`. And the rule that matters most, stated as the implementation rule verbatim: **a capability set that fails to load means no remote commands, not all of them.** That mirrors `setReviewProvidersLocked`, where a provider whose kind cannot be resolved is disabled and named in the startup warning rather than silently defaulting to CodeRabbit. A misconfigured `[remote]` does not listen and says so at startup.

*Reload.* `handleReload` rebinds or tears down the listener under `d.mu` when `[remote]` changed, following the pattern by which `d.native` is recreated.

*Secret discipline.* The daemon's TLS private key lives at `~/.lola/device.key`, 0600 inside a 0700 directory — **not** the macOS Keychain, because a launchd-started process cannot unlock the login keychain non-interactively and the daemon must come up headless. The APNs `.p8` is a path in config, never its contents. Nothing goes into `config.toml`, into argv (`ps(1)` reads argv), into a log line, or into a returned error. `internal/secrets/keychain_darwin.go` already passes secrets on stdin rather than argv; mirror that discipline.

*Bounded dispatch.* Each `req` frame dispatches concurrently — that is the point of the correlation `ID` — but behind a semaphore of four per connection. An authenticated device is not a trusted one: a stolen phone must not be able to fan out unbounded concurrent work on a daemon that spawns processes, execs `gh` and `tmux`, and holds `d.mu`.

*Capability tiers, and they are a CLOSED ALLOWLIST.* Stated once, unambiguously, because the permissive reading of this section is the one that gets someone hurt: **remote authorization is an allowlist keyed on `Cmd` and on frame `Type`. A command that appears in no tier is refused before `d.handle`, and adding a command to the daemon grants a phone nothing until it is written into a tier by hand.** There is no fallback tier and there is no "future commands automatically". `d.handle` has **twenty-seven** command names today, and every one of them is classified below or denied below; a Go test in `internal/daemon` walks the `switch` in `server.go` and fails when a `case` appears that no tier and no denial list names — the same shape as the existing `desktop/state_parity_test.go`, and for the same reason: there is no compiler in common between a `switch` statement and a policy table.

- `read` (6) — `status`, `sessions`, `projects`, `prs`, `tickets`, `pane`.
- `answer` (2) — `answer`, `resolveConflict`.
- `control` (14) — `review`, `coderabbit`, `dev`, `devFreePort`, `revive`, `pollOnce`, `enable`, `disable`, `open`, `openPr`, `openManual`, `openTicket`, `switchAgent`, `openURL`.
- `destructive` (1) — `kill`, with `Force` unconditionally cleared.

`openURL` is in `control` rather than `answer`, which is where an earlier draft had it, and the reason is worth stating: `internal/daemon/openurl.go` execs `open` **on the daemon's machine** behind nothing but an `http(s)://` prefix check. In the default-granted tier that is a remote party silently driving the developer's browser — one logged into GitHub, Linear and the corporate SSO — which is a drive-by primitive against every GET-actionable endpoint they hold a session for, plus a beacon, plus arbitrary attacker-chosen strings written into `daemon.log`, all with no desktop UI at all. It is also the wrong *behaviour* for a phone: a link tapped in a phone terminal should open on the phone. So the phone opens links locally, applying the same http(s)-only guard client-side (the guard is the point; the exec host never was), and remote `openURL` survives only as the deliberate "put this on my Mac's screen" action, in `control`, restricted to a URL the daemon itself surfaced in the current snapshot — a `SessionInfo.devUrls` entry, a PR URL, a Linear issue URL — and refusing anything else. The command's purpose does not require an open redirector.

**Denied to every remote device unconditionally, in code, not in configuration** — seven commands today, plus M2's five pairing commands:

- **`stop`** — severs the caller's own transport.
- **`kill` with `force: true`** — discards a dirty worktree, the single gate teardown has.
- **`renameProject`** — rewrites project identity; a config operation, and this phone does not do config.
- **`hookEvent`** — the dangerous one, and the one an earlier draft simply forgot. It is the *agent's own in-pane callback path*, and it is a remote write directly into the send-keys safety gate: `handleHookEvent` with `event: "stop"` sets `AtPrompt = true` **and** `AtPromptVerified = true`, then calls `flushHandoffsOnStop`. A single forged frame therefore (a) declares a mid-turn agent idle, defeating the `AtPromptVerified` protection `CLAUDE.md` spends more words on than any other invariant, and (b) immediately makes lola type stashed, attacker-influenceable review findings into a live agent's pane. `event: "session_end"` forges an `AgentExited` axis, which drives the reaction engine. Nothing about this path is remote by design; it must be unreachable from TCP by construction.
- **`reload`** — re-reads config and rebinds the listener the caller is speaking through.
- **`pairBegin`, `pairStatus`, `pairConfirm`, `devices`, `revokeDevice`** (M2) — enrolment and revocation are *local* operations at the desktop or the CLI. A paired phone that could enrol would let a thief add a second device that survives revoking the first; one that could revoke would let a thief cut off the operator's other devices. Pairing is opened by a human at the machine, which is the entire threat model.

**Frame types carry capability too, and the highest-privilege surface in this design has no `Cmd` at all.** Tiers keyed on `Cmd` never reach a `sub` or a `pty` frame, and a PTY write is raw bytes into an interactive process on the developer's Mac — strictly more powerful than anything in `destructive`. So:

- `sub` (pane subscription) and `pty` **read** require `answer`. This resolves an earlier contradiction in favour of the prose: pane subscription is *not* in `read`. A terminal *is* an answer channel and a read-only one is security theatre (tmux's own `-r` proves it — see *Read-only versus writable*), so a device that may not answer gets no pane stream.
- `pty` **write** requires `answer`, unconditionally, and is the single most sensitive frame in the protocol — it is also the one that deliberately bypasses the `AtPrompt` gate, so it is governed here or nowhere.
- A `-shell-N` or `-dev-N` pane requires the **named `shell` capability**, which *is* granted at enrolment (*Settled since drafting* (1)). A shell tab is a full interactive shell in the developer's checkout with their `gh` token, SSH agent and login keychain reachable: terminal write on one is *arbitrary code execution on the host*. Keeping it a separate capability rather than folding it into `answer` is still load-bearing — it is what makes "this phone may see terminals but not shells" expressible, what puts it in the device list where a human can see it, and what lets it be dropped from one device without unpairing it.
- `pair.*` frames are valid only inside an open pairing window and never on an enrolled connection.

**Authorization is checked per FRAME, not per connection.** The registry is an in-memory map, so this is free, and it is what makes a capability *downgrade* behave like a revocation: `lola devices grant` removing `control` takes effect on the device's next frame rather than whenever it next reconnects. The `epoch` check runs per frame for the same reason.

And the rule that must be normalization rather than validation, generalized past the one bool an earlier draft named: **`internal/remote` REBUILDS the `Request` rather than sanitizing it.** For each allowed command it constructs a fresh `protocol.Request` populated only from that command's own field allowlist, and discards everything else the phone sent. `protocol.Request` is a flat struct — `Poll`, `DryRun`, `Provider`, `Project`, `Ref`, `Session`, `Event`, `Detail`, `Hook`, `Force`, `Text`, `Lines`, `Args` — and every handler reads whichever fields it likes, so a remote `answer` frame carrying `Hook`, `Event` and `Force` reaches `d.handle` with all of them populated today. Stripping `Force` is a blocklist of one, and the justification for stripping it ("a future handler that forgets to check a capability must not be able to discard uncommitted work") argues against exactly that shape: a future handler that starts reading `Ref` or `DryRun` would get a phone-settable value for free. `Force` remains the named example — it is cleared on every remote `kill` — but the rule that survives a new field being added to `Request` is the rebuild.

*Audit.* Every mutating remote frame writes a log line naming the device id, the command, the session and the outcome — **and never the payload**. That exclusion is load-bearing, not fastidiousness: `answer` carries `req.Text`, which is prose a human typed at a phone and may contain a pasted token; `openManual`/`openTicket` carry prompt seeds; `openURL` already logs its full URL today. PTY bytes and resync frames are never logged at any level. Today the daemon cannot attribute a kill to anyone at all — `handleConn` does not even name its peer — and after-the-fact reasoning about a lost or stolen phone is impossible without this; it is the cheapest forensic capability in the plan and no existing client changes for it. Two consequences of the destination: `d.logf` writes `~/.lola/daemon.log` **and** mirrors to stderr through an `io.MultiWriter`, so a launchd stderr redirect is a second copy living outside the 0600 file, and the log is append-only and unrotated — now that a remote peer can drive writes into it, it needs a size bound or rotation. And the honest framing for the README: no *config* secret crosses this channel, but the pane stream and every resync frame carry whatever the agent has on screen, so the channel itself is secret-bearing. That is what the capability tiers are protecting.

*Rate limiting is on COST, not on mutation.* An earlier draft limited only mutating commands, which leaves the expensive ones unprotected and all of them are in the default-granted `read` tier: `prs` shells out to `gh`, `tickets` hits the Linear GraphQL API, `pane` execs `capture-pane`, `pollOnce` drives a whole tick. A `read`-only device looping `tickets` burns the operator's Linear quota; one looping `prs` burns the GitHub rate limit, which degrades **the daemon's own PR observation for every session** — a read-tier device denying service to lola's core function. So every command that egresses to a third party or execs gets a token bucket regardless of tier, alongside the mutating ones. The buckets are **per device, not per connection**, or opening four sockets multiplies the budget by four; concurrent connections per device are capped for the same reason, and the semaphore of four bounds concurrency within one connection but says nothing about rate. Burning the pairing window is not rate limiting: it protects enrolment, not steady state, and it has its own problem — see *Pairing*.

## Pairing

The desktop's Settings pane gains a "+ Connect app" button which calls `cmd=pairBegin` over the ordinary unix socket; `lola pair` does the same thing headless and prints a half-block QR to the terminal. The daemon, not the desktop app, holds the window. The QR payload is a string; **rendering it is the client's job** — the desktop draws an SVG in the frontend, the CLI prints blocks — so the daemon takes no QR dependency and ships a fact rather than a picture, matching how it treats every other derived value.

**Secret discipline for the pairing secret specifically, because lola has a way to leak it that no other project has.** `qr_secret` and the whole QR payload are never written by `d.logf` (which reaches `~/.lola/daemon.log` *and* stderr), never included in any response the daemon logs, and never placed in argv. The lola-specific hazard is `lola pair`: if it is run inside a lola-managed tmux pane — a `-shell-N` tab, which is exactly where a developer would run it — the daemon *reads that pane's text*. `attention.Classify` parses it, the observer captures it into the snapshot, `[statusagent]` ships pane context to a bounded `claude -p`, and `internal/brain` can summarise it. A live pairing secret would be sent to a third-party model and persisted in a JSON snapshot on disk. So `lola pair` refuses to print a QR when `$LOLA_SESSION` is set, naming the reason and telling the operator to run it in their own terminal; the 90-second TTL bounds the exposure but does not remove it, because the pane snapshot outlives the window.

The window is 90 seconds, single-use, one outstanding at a time, opened only by a deliberate human action, and the secret is zeroed on use, expiry or cancellation. An already-paired device can never enrol another.

### The sequence

Let `D` be the daemon's long-lived P-256 identity (`~/.lola/device.key`), which is also the subject of its self-signed TLS certificate. Let `P` be the phone's P-256 identity, generated at first launch inside the Secure Enclave (iOS) or StrongBox-backed Keystore (Android). P-256 rather than Ed25519 is not a preference: **the Secure Enclave holds P-256 and nothing else**, so an Ed25519 device key cannot be hardware-backed and would sit as extractable material readable by anything with code execution in the app process.

**1. Window opens.** The daemon generates `qr_secret` (16 random bytes, 128 bits) and `pairing_id` (16 random bytes), and returns the payload — **an opaque token, deliberately not a URI**:

```
lola1.<base64url of a CBOR/JSON blob>
  v    = 1
  id   = base64url sha256(SPKI(D))          // the FULL 32 bytes, 43 chars
  pid   = pairing_id                        // 16 bytes
  s     = qr_secret                         // 16 bytes
  addrs = ["192.168.1.5", "10.0.0.4", "fe80::1%en0"]
  port  = 7717
```

**The pin is the full SPKI hash, not a prefix.** An earlier draft carried `hex sha256(SPKI(D))[:8]` — eight hex characters, four bytes, **32 bits** — and specified the verification callback as a comparison against that. An attacker can grind a P-256 keypair matching a chosen 32-bit prefix in ~2³² hashes: minutes on commodity hardware, and precomputable against a daemon whose QR was seen once. Pinning would then contribute nothing and the transcript binding would be carrying the whole handshake alone rather than as defence in depth. A QR carries 43 base64url characters at no cost — that is the same optical-bandwidth argument the `qr_secret` decision rests on, applied consistently. The comparison is full-length and constant-time, over **bytes**, and the plan says "bytes" because "`[:8]`" is precisely the ambiguity that produces a 32-bit pin in one implementation and a 64-bit one in another.

**And it is not a `lola://` URL.** Custom URL schemes cannot be claimed exclusively on either platform: any installed app may register `lola://`, resolution is roughly first-installed-wins on iOS, and users routinely scan QR codes with the **system camera** rather than an in-app scanner — at which point the OS hands `qr_secret` and `pairing_id` to whichever app claimed the scheme. Choosing a URI form actively invites that path. So the payload is an opaque token that only Lola's in-app scanner understands, the system camera produces nothing useful from it, and `qr_secret` is never handed to the OS URL router. (If a tappable QR is ever wanted, the only exclusively-claimable form is a Universal Link / App Link on a domain under the project's control — that is a decision with an infrastructure cost attached, not a free upgrade.)

The 128-bit `s` is the whole security argument, and it is CTAP 2.2 hybrid's model — that protocol's QR carries a compressed public key *and* a 16-byte random secret, and consequently has no short authentication string at all. A QR is a high-bandwidth optical channel; deliberately throwing that bandwidth away in favour of a six-digit code and then needing SPAKE2 or CPace to compensate is strictly worse, and there is no credible maintained Go PAKE to compensate with — every SPAKE2/CPace repository found is a hobby project under thirty stars, and PAKEs fail silently when point validation is wrong.

`addrs` carries every non-loopback address so that discovery is an optimisation and never a dependency. Access-point client isolation, guest and corporate SSIDs, multi-VLAN networks and mDNS-blocking APs all break Bonjour; none of them break a QR-carried address, and the app accepts a manually typed `host:port` as a third path. What is pinned is the **key**, never the address, so roaming between networks costs nothing.

**That is a statement about trust, not about reachability, and reachability needs its own answer before M6.** The QR's `addrs` are captured at enrolment; mDNS is M6 and strictly optional. So from M2 through M5 the phone would hold exactly one address list frozen at pairing time, and a DHCP lease change, a new SSID, or a laptop moving between home and office silently bricks the app with no named failure. It also undercuts M3's own "a daemon restart is survived by the client": a restart on a new lease is not survived. Each device therefore keeps an **address book** rather than an address: the pairing addresses, plus last-known-good, plus a manually entered `host:port`, plus mDNS entries once M6 lands. The connect attempt walks it in that order with a short per-entry timeout, and "the key is valid, nothing answers" is a **named UI state** — "can't reach <hostname>", with the address book editable — which must never render as the pairing screen, because that is what revocation looks like and the two failures need opposite responses. Pulling `internal/discover` forward from M6 is worth considering for exactly this reason: the QR-carries-addresses argument makes discovery optional for *pairing*, not for *reconnect*.

**2. Connect.** The phone dials `wss://<addr>:<port>` with TLS 1.3 only, ALPN `lola/1`, and `ws://` refused unconditionally. Server-certificate verification is a custom callback comparing `sha256(SPKI(server))` to `id` from the QR — **SPKI, not the certificate DER**. Pinning the certificate pins the wrong object: it breaks on any certificate regeneration and forces a full re-pair on a daemon reinstall, while the key is the thing that actually authenticates.

The phone presents its own certificate over the same handshake, so the daemon's pre-authentication surface is the TLS stack rather than a WebSocket upgrade, a JSON parser and an envelope decoder. During the pairing window only, the daemon accepts any client certificate; in steady state it requires the presented SPKI to be in the registry.

**3. Transcript and SAS.** Both sides compute, from what each of them *observed*. **Every field is length-prefixed** (a `uint16` big-endian byte count before each), and the rule is general: a later addition must not be able to introduce a concatenation ambiguity, which a bare concatenation of today's happens-to-be-fixed-length fields invites the first time someone appends a string.

```
transcript = "lola-pair-v1"
           || LP( sha256(SPKI of the certificate seen as SERVER) )
           || LP( sha256(SPKI of the identity seen as CLIENT) )
           || LP( qr_secret )
           || LP( pairing_id )
           || LP( n_phone )          // 32 random bytes, sent in HELLO
           || LP( n_daemon )         // 32 random bytes, sent in HELLO
           || LP( daemon_hostname )  // exactly the string the PHONE will display
           || LP( phone_name )       // exactly the string the DAEMON will display
           || LP( phone_platform )

prk     = HKDF-Extract(salt = qr_secret, ikm = transcript)   // crypto/hkdf, Go 1.24+
k_proof = HKDF-Expand(prk, info = "lola-proof-v1", 32)
sas     = HKDF-Expand(prk, info = "lola-sas-v1",   3)        // 24 bits derived
n       = uint24 big-endian over sas[0..2]
emoji[i] = TABLE[(n >> (18 - 6*i)) & 0x3F]                   // i = 0..2, TOP 18 bits; low 6 discarded
```

Four details are pinned because Swift and Kotlin must reproduce this byte-for-byte against published Go vectors, and each is exactly the kind of thing that diverges silently. The proof key is its own **Expand** output rather than the PRK itself, so no HMAC key is ever the same value another published output was expanded from — it costs nothing and removes the question. HKDF is used "inverted" here (the shared secret is the salt, the transcript is the IKM); that is safe *because `qr_secret` also appears inside the transcript*, and it is written down rather than left as a coincidence someone later "cleans up". The SAS integer is **big-endian over three bytes**, the **top** 18 bits are used and the low 6 are discarded. And the proof send order is fixed: **phone first, then daemon.**

**Every string either side shows a human during confirmation is in the transcript.** The daemon's hostname and the phone's model/name are what the operator actually reads at step 5, and in an earlier draft neither was bound to anything — so an attacker supplied whatever model string made the operator comfortable. That directly contradicted this section's own strongest argument, which is that what matters is binding *what each side observed*; the argument was applied to the SPKI hashes and not to the strings a person is being asked to judge. It applies to both now, and the general rule is the one to keep when a field is added later.

Three emoji from the Matrix 64-emoji table, used verbatim including its descriptions — that table is already vetted for colour-blind legibility, cross-cultural recognition and absence of unfortunate connotations, and re-deriving one is pointless work with a real failure mode. Eighteen bits is worthless against a guessing attacker and that is fine: an attacker without `qr_secret` cannot complete the handshake at all, so the emoji never has to resist guessing. Matrix needs seven emoji because its Diffie–Hellman is unauthenticated and the SAS is its only MITM defence; ours is confirmatory. **If the QR is ever weakened to a typed code, this must become a real PAKE and at least seven emoji — the two decisions are one decision.**

Including both SPKI hashes in the transcript, each side using what it observed, is what makes a relay MITM fail even if the pin callback is buggy. In a relay, the phone sees the attacker's server SPKI while the daemon sees its own; the transcripts differ, the proofs mismatch, the window burns. This is the single most important line in the section and none of the three source proposals had it in this form — one omitted the certificate binding entirely and rested everything on the pin callback being correct, which is the easiest thing in mobile TLS to get wrong.

**Note on the TLS exporter.** Two proposals derived `ikm` from `ConnectionState.ExportKeyingMaterial`, which is the textbook answer and which Go provides. Neither named a *client* stack that exposes it — Network.framework and URLSession do not, and the research was unable to confirm one for Android either. Rather than build a protocol on an API nobody has verified, this design uses only values both sides demonstrably possess: the certificates they saw, the secret they share, the nonces they exchanged. The exporter is not used, not optional, and not negotiated; a negotiated binding would be a downgrade surface. This is a deliberate departure from the security judge's preferred mechanism while keeping the property that mechanism exists to provide.

**4. Proofs.** Each side sends `HMAC-SHA256(k_proof, "phone-proof")` / `HMAC-SHA256(k_proof, "desk-proof")` (phone first) and a P-256 signature over the transcript with its identity key. All comparisons are constant-time.

A mismatch does **not** burn the window on the first try, and that is a correction rather than a relaxation. Burning on the first wrong proof turns fail-closed into a self-inflicted denial of service: during the window the daemon accepts any client certificate, so any peer that can reach the port can burn every pairing window the operator opens, with one packet, indefinitely — and the operator sees only "pairing failed", indistinguishable from a bad scan. So the window allows **three** proof attempts (still nothing against 128 bits), the pairing path gets its own connection-attempt rate limit and a cap on concurrent pairing connections, and the two burn conditions are distinguished in the text and in the UI: a window burns on a **completed enrolment or expiry** (correct), while repeated wrong proofs close it with a message that says *someone else on this network is attempting to pair* — not "scan failed", because the operator's next action is different in each case.

**5. Confirmation, and the desktop's half is a SELECTION, not a yes/no.** The phone shows the three emoji with their names plus the daemon's hostname; the desktop shows the phone's model and name and **three candidate emoji rows, one of them real**, asking the operator to tap the row their phone is showing. A yes/no dialog is confirmable by reflex with no phone in hand, which is exactly the situation the live-QR-observation attack creates (see *Threats*); a 1-of-3 selection cannot be. Either side answering "none of these" / "no" aborts and burns the secret. Both must agree.

**6. Enrolment.** The phone sends `ENROL{name, platform, push_token?}`; the daemon appends `{id, spki_sha256, name, platform, caps, paired_at, last_seen, epoch, push_token, push_watermark}` to `~/.lola/devices.json` and replies `ENROLLED{device_id, epoch, caps}`. Default capabilities on first enrolment are `read`, `answer`, `control`, `destructive` and `shell` — every tier — per *Settled since drafting* (1) and (2). They are still *named* per device and still individually revocable or downgradable from the desktop's device list or via `lola devices grant`/`revoke`; what changed is only the default, and the reason it can change is that revocation, not a withheld capability, is the answer to a lost phone. Enrolment is a deliberate physical act at the desktop, so a device that got through pairing is one the operator meant to trust.

`name` and `platform` are attacker-supplied strings that get stored, rendered in the desktop device list and shown to the operator during confirmation, so they are **clipped and sanitized at the boundary** exactly as this repo already treats a watch provider's configured author (`botDisplayName`): a stated maximum length and a restricted character set, applied before anything renders them.

Enrolment ends with a **loud, unmissable desktop notification** and an audit line, and the device list shows "enrolled N minutes ago" prominently at the top. An enrolment the operator did not perform must be *discoverable* — that, plus the 1-of-3 selection, is what actually answers the observed-QR attack, because the SAS cannot.

If enrolment finds an existing entry with the same declared `name`/`platform`, the desktop offers to **replace** it rather than adding a second. The operator is standing there confirming anyway, and the alternative is a registry that accumulates live credentials forever — see *Revocation, rotation, expiry*.

**7. Steady state.** The same WSS handshake without `qr_secret` and without the SAS. Mutual TLS with the registry check does the authentication, and a fresh daemon-chosen nonce inside a signed reconnect transcript does the freshness, so a reconnect cannot be replayed even on a platform or path where mutual TLS turns out to be unavailable. Session tickets are disabled and 0-RTT is off — replaying a side-effectful control frame is a real attack shape, and although Go's `crypto/tls` server implements no 0-RTT today, a protocol whose safety depends on a library not implementing an optional feature is not a safe protocol.

### Key storage

**iOS.** P-256 in the Secure Enclave via `kSecAttrTokenIDSecureEnclave`, accessibility `kSecAttrAccessibleAfterFirstUnlockThisDeviceOnly`. `AfterFirstUnlock` so background reconnect works on a locked phone; `ThisDeviceOnly` so a device-bound key never syncs to iCloud Keychain. **No biometric gate on the key itself** — a gated key breaks reconnect, users then disable pairing, and the feature dies.

**Privileged actions are gated in the PLUGIN, not in the WebView.** This is the one place where an earlier draft contradicted itself: it correctly argued that "the plugin, not the WebView, holds the capability tier", and then placed the only real mitigation for a stolen unlocked phone in the WebView ("the UI re-authenticates with biometrics before `destructive`"). The UI is the Svelte app that also renders untrusted PTY bytes through xterm.js — the exact component named in the compromise scenario — and a compromised or merely buggy WebView simply does not call the prompt, after which the frame goes out anyway. So `LolaTransport` refuses to *emit* a `destructive`- or `switchAgent`-tier frame without a fresh `LAContext` (iOS) / `BiometricPrompt` (Android) success, and the WebView cannot bypass it because the WebView never constructs the frame. The validity window is stated so "authenticate once and the app is unlocked forever" does not become the implementation: **60 seconds, one privileged action per success.**

**Android.** Keystore EC P-256 with `setIsStrongBoxBacked(true)` and a `StrongBoxUnavailableException` fallback to TEE, `setUserAuthenticationRequired(false)` for the same reason.

**Daemon.** `~/.lola/device.key`, 0600 in a 0700 directory. The registry `~/.lola/devices.json` is not secret but is 0600 anyway and is written atomically temp+rename, exactly as `session.Store` writes its snapshot.

### Revocation, rotation, expiry

Authentication is per-connection SPKI-in-registry and authorization is per-frame, so revocation *and* downgrade are instant and real rather than aspirational. `lola revoke <id>` (and the desktop device list) drops the entry, bumps the global `epoch`, and closes every live connection holding that key with WebSocket code `4403`. The phone treats `4403` as terminal: it wipes its Keychain entry and returns to the pairing screen.

**The `epoch` must live OUTSIDE the file it is meant to protect.** Its stated purpose is that a stale copy of `devices.json` — a restored backup, a synced dotfile — cannot resurrect a revoked device. An earlier draft stored it *inside* `devices.json`, which is backwards for exactly that threat: restoring the file restores the old epoch alongside the resurrected entry and the check passes. It is therefore a monotonic counter persisted beside `device.key` in the 0700 directory, the daemon takes `max(stored, observed)` on load, and it **refuses to move backwards** — so a restored older registry cannot lower it. Rotation is a new key plus a re-pair; there is no key-update protocol, because one would be a second enrolment path to get wrong for a saving of thirty seconds.

Pairing windows expire at 90 seconds. Device entries do not expire on their own, and that rule stays — silently un-enrolling a device makes the failure mode "it stopped working and nothing said why". But the no-expiry rule needs a visibility half, because **re-pairing is a guaranteed flow rather than an edge case**: Secure Enclave keys are never backed up and `ThisDeviceOnly` blocks sync, so an OS reinstall, a device replacement or a restore to new hardware *always* produces a new device key and a new enrolment. Without help, every one of those leaves the old entry authorized forever, holding a stale push token — and that old entry is precisely the credential an attacker who extracted a key before the wipe would present. So: enrolment offers to replace a matching existing entry (step 6), entries with a stale `last_seen` sort to the top of the device list with a one-tap revoke, and the README documents "replaced your phone" as a known operation rather than a surprise. The fix is visibility, not automatic deletion.

**Push tokens rotate**, so there is an authenticated `updatePushToken` frame that can write **only the calling device's own record**, never another's, and that changes neither capabilities nor the watermark. Without it, either notifications silently stop after an app reinstall or one device can redirect another's.

### Threats and what stops them

*An unpaired laptop on the same café WiFi.* Mutual TLS with a registry check rejects it inside the TLS stack. It never reaches the WebSocket upgrade, the JSON parser or the envelope decoder. This is the whole reason mutual TLS is worth the plugin work rather than server-auth-only.

*A relay MITM during pairing.* Both observed SPKI hashes are in the transcript, so the proofs mismatch and the window burns — with no dependence on the pin callback being correctly implemented.

*Online guessing of the QR secret.* Constant-time comparison, and the first failure invalidates the entire window. One guess against 128 bits.

*A stale or screenshotted QR.* Single-use, 90-second TTL, zeroed on cancel. A second concurrent window cannot exist.

*A QR observed LIVE — screen share, a recorder, a camera in the room, a shoulder.* This is the case the threat table used to skip, and it is the one where the SAS provides **no protection at all**. `qr_secret` is a bearer credential displayed on a screen for 90 seconds; an attacker who reads it and connects first completes the handshake and burns the window, and the victim's own phone then fails with "pairing failed" — indistinguishable from a bad scan. Meanwhile the desktop shows a confirmation carrying a device model the *attacker* chose. The user has no second screen to compare emoji against, because their own phone never got that far, so a yes/no confirmation here is not a comparison but a decoration on an attacker-controlled dialog. Four things answer it, none of them the emoji: the desktop confirmation is a **1-of-3 selection** rather than yes/no, so a user with no phone in hand cannot confirm by reflex; the displayed identity strings are **in the transcript**, so they are at least authenticated to whoever completed the handshake; enrolment fires a **loud desktop notification plus an audit line** and the device list foregrounds "enrolled N minutes ago", so an enrolment nobody performed is discoverable and one-tap revocable; and the 90-second window should be shortened once the real scan-to-confirm path has been measured on a device — it was chosen as a guess, not from data.

*Two desktops in one room, or a wiring bug.* This is what the three emoji actually catch, and it is the realistic failure the SAS exists for.

*A pairing window burned by a stranger on the network.* Three proof attempts rather than one, a rate limit and a concurrency cap on the pairing path, and a distinct operator-facing message — see step 4. Fail-closed must not mean "any peer on the LAN can prevent pairing forever".

*Replay of a `kill` frame.* Ephemeral handshake per connection, session tickets disabled, 0-RTT off.

*A stolen but unlocked phone.* The weakest point in the design, and it is weak. `setUserAuthenticationRequired(false)` means the key signs without a person. Say plainly what that buys an attacker at the *default* grant: `read` plus `answer`, and `answer` includes the pane subscription and the PTY write channel — so **a default-granted phone can type into a live agent**, which is not "cannot kill or spawn", it is materially more than anything in `destructive`. If that device also holds the non-default `shell` capability, the attacker has arbitrary code execution on the developer's Mac through a `-shell-N` tab, with their `gh` token and SSH agent in reach. That is the honest framing, and it is why `shell` is not granted at enrolment and why the terminal is gated at `answer` rather than `read`. Mitigations, none of them complete: capability tiers bound what any one device can do and are enforced per frame; the `Request` is rebuilt at the boundary so `Force` can never reach `d.handle`; **biometric re-authentication is enforced in the plugin** (60 s validity, one action per success) in front of `destructive` and `switchAgent`, not in the WebView; the audit line makes reconstruction possible; per-device rate limiting bounds the damage rate; revocation and downgrade from the desktop take effect on the next frame. **The maintainer has decided this is acceptable** (*Settled since drafting* (1), (2), (4)): the defaults are permissive because the recovery action is revocation from the desktop, which bumps the `epoch` and kills the device on its next frame regardless of where the phone is. That places a hard requirement on M2 — the device list must be one obvious action away in the desktop app, and "Disconnect" must not be buried behind a settings tab nobody opens under stress. It also raises the value of the audit line, since after a revocation the only way to know what the device did is the log.

*A compromised WebView.* The capability-holding session lives in a WebView that also renders untrusted PTY bytes through xterm.js, and the security review is right that this is a real chain. Three things bound it. The desktop app already accepts exactly this risk today and is *more* privileged — it holds an unauthenticated unix socket with all twenty-seven commands and force-kill available — so this is not a new risk class, and if the argument were fatal it would be fatal for the shipped desktop. The device key never enters JavaScript: it lives in the Secure Enclave and is used only by the native plugin, so a script-execution flaw cannot exfiltrate an identity, only misuse a live session. And the plugin, not the WebView, holds the capability tier *and the biometric gate*, so such a flaw cannot escalate past what the device was granted. That is defence in depth the desktop does not currently have.

*The daemon's own listener as an attack surface.* This is the honest framing that belongs in the README: `answer` and `openManual` type caller-supplied prose into an autonomous coding agent with filesystem and network access. `[remote].enabled = false` is the default for that reason, and `bind = "localhost"` exists so a user who only wants this over a tunnel can have it.

## Terminals on a phone

**Wire shape per pane.** `internal/panebus` runs exactly one `tmux -L lola attach-session -t "=<name>" -f ignore-size` per pane name, through `vtterm.New` so the daemon holds a live model of the screen, and fans the bytes out to every subscriber. Two phones cost one tmux client. Subscribers get, in order:

1. **One `resync` frame** built from the shadow emulator's `Render()`, `Cursor()` and `AltScreen()`. This is what `internal/vtterm` is worth to this project and it is the reason it is in the table above: an agent runs on the **alternate screen**, where a fresh `tmux attach` replays nothing, so without a prelude a subscriber stares at a blank pane until the agent next repaints. The two rival proposals answer this with a `capture-pane -p -e -S -N` prelude, which is strictly weaker — `capture-pane` carries no cursor position and no cursor shape, and the cursor is precisely what you need to see in order to answer a prompt. The emulator also solves resume: a raw byte ring can hand a waking phone a stream that begins mid-escape-sequence, whereas a rendered frame is always coherent.
2. **Raw PTY bytes**, base64 inside `pty` frames, coalesced on a 16 ms tick — identical to `TermService.flushLoop`, so an idle pane costs zero bytes. A busy agent costs 5–50 KB/s; a full colour redraw of an 80×40 screen costs 10–30 KB. That is strictly better at rest than the desktop's own 1.4-second `capture-pane` poll, which costs roughly 5 KB/s per pane even when nothing is happening.

**The pane name is an untrusted string that reaches a tmux argv, and it is resolved before any exec.** `Attach(pane string, ...)` ends in `tmux -L lola attach-session -t "=<name>"`; the `=` exact-match prefix stops globbing and stops nothing else. So `panebus.Attach` first resolves the name against the session store **and the requesting device's visible set**, and rejects anything not matching `^lola-[a-z0-9._-]+(-shell-\d+|-review|-dev-\d+)?$` — anchored at both ends, the same discipline the teardown invariant already demands, and which also refuses a name beginning with `-` that tmux would read as a flag. A `-shell-N` name additionally requires the `shell` capability. An unresolvable name fails closed. Without this a device can enumerate and attach panes belonging to sessions it was never shown, including another project's shell tab.

This requires two additions to `internal/vtterm`: a `Tap(func([]byte))` invoked in `readLoop` before `emu.Write`, so the bus can forward the same bytes it models, and a size-tracking path (below). The `Tap` is about fifteen lines and does not disturb the TUI's use of the package.

**The shadow emulator must be resized, or the resync frame — the whole reason `vtterm` is in this design — renders wrong.** `vtterm.New(cmd, w, h)` fixes the grid at construction and only `Term.Resize(w, h)` changes it. The tmux *window* size moves under panebus's feet whenever the desktop attaches, detaches or resizes (`desktop/termsvc.go`'s `Attach` passes no `-f` flag, so the desktop does drive it). So panebus owns the size explicitly: the attach PTY is sized to the **window**, `#{window_width}`/`#{window_height}` (equivalently the PTY's SIGWINCH) is the size source, panebus calls `Term.Resize` on every change, and every subscriber is sent a **fresh `resync` frame** across a resize — the frame type already supports it. "The desktop resizes its window mid-stream and the phone recovers a correct frame" is in M1's definition of done, because it is cheap to test and because the failure otherwise gets diagnosed as "xterm.js can't do this".

**The sizing problem, and its exact solution — all panning is CLIENT-side.** tmux sizes a *window*, not a client, and lola's `ConfigureServer` sets only `history-limit` and `mouse`, so the effective policy is tmux's default `window-size latest`: the most recently active client wins. A phone attaching normally to the desktop's 200-column pane would collapse it to roughly 40 columns and mangle the agent's TUI on both screens. The fix is `attach-session -f ignore-size`, whose man page says of the client that *"the client does not affect the size of other clients"*. Precisely: the phone cannot shrink the window. (Under `latest` a desktop re-attach still resizes it, which is fine and correct — the claim is that the *phone* cannot, not that the size is frozen.)

Because there is exactly **one shared attach per pane**, there is no per-phone tmux client to size or to pan, and an earlier draft's `refresh-client -U/-D/-L/-R` panning contradicted its own fan-out architecture: `refresh-client` viewport state and `-c` cursor tracking are per-*client*, so two phones on one shared client would fight over one viewport and each user's drag would scroll the other's screen. So panebus attaches at the **full window size**, fans out the **complete untruncated byte stream**, and every subscriber renders that full grid into its own xterm.js and pans **client-side** — a two-finger drag moves the phone's own viewport over a locally-held 200-column screen, which is also the only version that stays responsive on a phone. `refresh-client` and `#{window_bigger}` drop out of the design entirely; the "200 cols · panning" chip becomes a client-side derivation from `term.cols` against the frame width, so truncation is still never a mystery. The cost is bytes for columns the phone is not currently looking at, which is the same cost the desktop already pays and is bounded by the 16 ms coalescing.

**Font scale is the phone's own control, and it does not remove the need to pan.** Fitting 200 columns onto a 390pt screen means roughly a 2pt cell — unreadable — so the phone's answer is a legible cell size plus a two-finger pan over the locally-held grid, with pinch-to-zoom stepping the xterm.js `fontSize` between about 8pt and 16pt and re-fitting on `document.fonts.ready` exactly as the desktop already does. Zooming out far enough to see the whole width is *offered* and is useful for orientation, not for reading. This was raised as "can it just scale the font down" and the answer is: partly, and the pan is the other half.

A **"Fit to phone"** toggle remains, and it is now the *only* thing that touches tmux sizing: it drops `ignore-size` so the phone's dimensions drive the window, offered only when no other client is attached — the common case when you are genuinely away from the Mac. (The alternative shape, one attach per subscriber, would restore per-phone tmux-side sizing at the cost of a tmux client per phone and of the "two phones cost one tmux client" property; it is not chosen, and it is written down here so the trade is visible if the client-side pan disappoints on device.) Setting a global `window-size largest` was considered and rejected: `ConfigureServer` is the ONE place lola sets a global tmux option, every session-creating caller must build its client through `config.TmuxClient` or the next spawn resets the server, a global tmux has dropped only logs an advisory on every spawn, and it would need the same retry-on-cold-server treatment `history-limit` has — a large blast radius for something client-side panning already solves.

The research quoted the `ignore-size` man page but nobody tested three concurrent clients (desktop, phone, a stray CLI `tmux attach`). That verification belongs in M1.

**Scroll is an RPC and never client-synthesized keys.** `pty{action: "scroll", lines: n}` calls `tmux.ScrollPane`, which asks the pane once — `display-message -p '#{pane_in_mode} #{mouse_any_flag} #{pane_width} #{pane_height}'` — and either writes SGR wheel events to the *program* (an alternate-screen application keeps its own transcript and asks for the wheel) or enters `copy-mode -e` and scrolls tmux's history (a plain shell, whose history *is* tmux's). Getting this wrong is not a degraded scroll but no scroll at all: copy mode on an agent pane reads `[0/0]` and moves nothing. That decision is server-side by design and the phone must never re-derive it. The unanswerable case fails toward copy mode, which is the half that cannot type into a program by accident.

`LiveTerminal.svelte`'s custom wheel handler must keep returning `false`. xterm's alternate-screen fallback converts a wheel event into cursor keys, which walks the *agent's input history* — that is the "the terminal is not scrollable" bug as users actually meet it.

**Writes are raw PTY bytes, and that is a deliberate exception.** A live terminal a human is typing into writes straight to the PTY master, exactly as `TermService.Write` does, preceded by a copy-mode cancel on the first keystroke after a scroll (copy mode is a property of the pane, so it outlives the wheel that entered it, and keys delivered to a scrolled-back pane are read as copy-mode *commands* and silently lost). The `scrollMu` lock is held **across** the write, not just across the flag, so a concurrent scroll cannot slip copy mode in between the cancel and the keystroke.

This path **bypasses the `AtPrompt` idle gate, by design.** The gate exists to stop lola's *automation* — reactions, review hand-offs, `resolveConflict` — from typing into an agent mid-turn and corrupting it. A human at a keyboard is the case the gate was never about; the desktop app already works this way, and a phone that could not send Ctrl-C mid-turn would be useless. This must be written down as a deliberate human-in-the-loop exception rather than papered over with a claim that the phone "never goes near tmux", because a false claim about the gate is how the gate gets deleted later by someone tidying up. The `answer` and `resolveConflict` *commands* remain gated exactly as they are today; only the live terminal is exempt, and only because a person is holding it.

**One UI-level guard, and it is friction rather than a gate — do not confuse the two.** The phone is not equivalent to the desktop in the way that argument assumes: the desktop human sees the full 200-column pane, while the phone human sees roughly 55 columns of it with panning, so typing into a mid-turn agent from a clipped view is materially more likely to be an accident than doing it at the Mac, and the damage is exactly what the gate exists to prevent. So when the daemon's own pane classification is **not** `ActivityWaiting`, the phone requires a deliberate "send anyway" before the first keystroke of a burst; Ctrl-C and Escape are exempt, because interrupting is the legitimate mid-turn action and adding friction to it would recreate the uselessness the exception exists to avoid. It is human-in-the-loop friction in the client, it is **not** the `AtPrompt` gate, and it is labelled that way here so nobody later deletes one believing it is the other.

**Link activation opens on the PHONE.** `LiveTerminal.svelte` already wires `WebLinksAddon` for plain-text URLs and `term.options.linkHandler` for OSC 8 hyperlinks, and the *guard* carries over unchanged: http(s) only, because terminal text is untrusted — a log line can print `file://` or `javascript:`. What does not carry over is the exec host. `cmd=openURL` runs `open` on the **daemon's** machine, so routing a phone tap through it would silently launch Safari on an unattended desktop, which is both the wrong behaviour and a small remote-nuisance primitive; see the `openURL` note under *Capability tiers*. The phone applies the same prefix check client-side and opens locally. Note also that with `[tmux].mouse = true` tmux grabs mouse events and clicks never reach xterm at all; that option is off by default and should stay off.

**Scrollback** is therefore three things, and only the first is new: the shadow emulator's current screen (the resync frame), the program's own transcript reached by the scroll RPC on an alternate-screen pane, and tmux's copy-mode history on a plain shell pane. xterm.js's own scrollback buffer stays empty on an agent pane and that is correct — nothing should be written into it.

**Link activation goes through the phone's own opener.** See the paragraph above; the guard survives, the exec host does not.

**The keyboard accessory bar.** Termux's model, because it is the one whose mechanics are readable in source and because every serious mobile terminal converges on it. Two rows, the second collapsible:

```
row 1:  Esc   Tab   ⇧Tab   ↑ ↓ ← →   ⏎   ⇧⏎
row 2:  Ctrl  Alt   ^C ^D ^Z ^R   Home End   PgUp PgDn   y   n
```

Modifiers **latch**: tap `Ctrl`, then `c`, and the next ordinary keypress consumes the modifier and clears it. A modifier you must hold is unusable on glass. Long-press repeats at 200 ms to first repeat, 80 ms thereafter, which matters for arrows. Long-press on a key may offer a second glyph, which doubles a row's density without a third row.

The exact bytes, because getting any of them wrong is a silent failure: Enter is `\r` (CR, never LF). Shift+Enter is `\x1b\r` (ESC CR) — neither xterm nor any other layer consults shift for Enter, so the handler synthesizes the pair and swallows the event; fixing it up in `onData` is impossible because the modifier is gone by then. Escape is `\x1b`. Ctrl-C/D/Z/R are `\x03`, `\x04`, `\x1a`, `\x12`. Tab is `\t`; **Shift-Tab is `\x1b[Z`**, which is how Claude Code cycles permission modes and is not optional. Backspace is `\x7f` (DEL, not `\b`). Pasted text is wrapped in bracketed paste, `\x1b[200~` … `\x1b[201~`, or a pasted stack trace submits at its first newline.

**Arrows must not be hardcoded.** They are `\x1b[A`/`\x1b[B`/`\x1b[C`/`\x1b[D` in normal cursor mode and `\x1bOA`/`\x1bOB`/`\x1bOC`/`\x1bOD` when the application has set DECCKM, and a real emulator tracks that mode from the *output* stream. So the accessory bar's arrow buttons synthesize a `KeyboardEvent` into xterm.js's own key handling rather than writing bytes to the PTY, and xterm resolves the mode. This is not a nicety: the AskUserQuestion picker is arrow-plus-Enter driven, and it is the second most important thing on the phone after a yes/no.

**Read-only versus writable.** Every pane the phone can see is writable, and there is no read-only mode. tmux's `-r` flag is `-f read-only,ignore-size`, and in read-only mode only keys bound to `detach-client` or `switch-client` do anything — so a read-only attach cannot deliver the one capability the terminal exists for. The distinction that actually matters is a capability one, and it is enforced on the **frame type** rather than on a `Cmd` (see *Capability tiers*): a device without `answer` gets no pane subscription and no terminal screen at all, because a terminal *is* an answer channel and pretending otherwise would be security theatre; a `-shell-N` pane needs the separate `shell` capability on top. What is genuinely read-only is the multi-pane overview, which stays on `CaptureMany` snapshots — many panes, low fidelity, one round trip — and is the right protocol for tiles even though it is the wrong one for the pane you type into.

## Notifications

There is no cloud backend and there will not be one. iOS suspends a backgrounded socket within roughly thirty seconds and the VoIP socket path was removed in iOS 13, so a phone that is not in the foreground cannot be woken by the daemon holding a connection open. **The daemon must push, and the daemon itself is the push sender.** `internal/push` speaks HTTP/2 directly to APNs with a `.p8` ES256 token — no Firebase, no relay, no third party, and no inbound connectivity required, since the daemon is the client of Apple's endpoint. Android gets no push at all (*Settled since drafting* (5)): FCM would mean a Google Cloud project and a service-account dependency chain, which is exactly the cloud backend this design refuses. The consequence is not hidden — an Android device is a same-network, foreground client with no wake path, and Doze closes its socket when the screen does. If that proves intolerable in use, the decision to revisit is FCM, and nothing else in this section changes.

Push is a **third channel** beside desktop and Slack, not a new notification model — but the integration is not quite "register `internal/push` behind `notify`'s existing interface", because that interface cannot express it and `Notify`'s timing forbids it. `notify.channel` is **unexported** and `New` builds its channels from a hardcoded set inside the package, so no external package can register one without changing `notify`. More fundamentally `channel.send(ctx, Note) error` has **no device dimension** at all, while push needs per-device tokens, per-device priority preferences and the per-device watermark below. And `notifier.Notify` blocks on `wg.Wait()` until every routed channel returns (15 s per-channel cap) and is called from `internal/daemon/reactions.go` on the reaction path — an APNs fan-out to N devices there would stall the observer's reaction work for every session.

So the shape is: a `pushChannel` **inside** `internal/notify`, holding an injected `push.Sender` seam, which **enqueues and returns immediately** so `Notify` stays fast and `notify` keeps both its leaf status and its unexported interface. Everything device-shaped — the fan-out, the token list, the watermark, the per-device priority preferences — lives in `internal/push` behind that seam. The device list comes from `internal/devices`, which `notify` must not import; that is precisely why it arrives as a seam rather than a dependency.

What is worth waking a phone for, and at what weight:

- **Urgent, time-sensitive.** A parked agent (`needs_input` with `inputReason` in `question` or `idle_notification`) and quota exhaustion or agent fallback. These are the two states where everything stops until a person acts, and both are one tap away from resolved.
- **Action.** `escalated` CI failure — bare `ci_failed` is noise while the reaction engine still retries, and `escalated` is exactly the field that says the retries are spent. Also `changes_requested`, a review pass that found issues, an unexpected `dead` session (with Revive offered inline), and `needs_input` with `inputReason` of `permission_prompt` or `dialog` — alertable, but with no answer affordance, because prose is the wrong reply.
- **Info, digest only.** `approved` plus green checks, and merged-and-cleaned-up. Batched, never an interrupt.
- **Never.** `working ↔ idle` churn, `draft`, `ci_pending`, `review_pending`, `orphaned`. `state.Notable(from, to)` is already the correct feed filter; push is a strictly smaller subset of it.

**Payloads are opaque, and "opaque" means a HANDLE, not a session id.** A push notification travels through Apple's and Google's infrastructure, and lola's notification text carries Linear issue identifiers, PR states and session titles. The obvious payload — "a session id, a category and a priority" — is *not* opaque: `runtime.SessionID` is `"lola-" + project + "-" + strings.ToLower(identifier)`, so a session id is literally `lola-okane-nor-373` and Apple and Google would learn the operator's project names and Linear team prefixes from every single push. The payload therefore carries a **per-device opaque handle** — a random id minted daemon-side, mapped to the session in `devices.json`, never leaving the paired channel — plus a category and a priority, and nothing else. The app fetches the human-readable content over the paired channel after unlock, using the notification-service extension where a preview is wanted. This costs a round trip on a notification tap, removes third-party infrastructure from the set of things that see what you are working on, and makes M5's definition of done a fact rather than an aspiration. (Rotating the handle per notification is the further step if unlinkability across pushes matters; the plan does not currently require it.)

**Dedup needs a persistent watermark.** `SessionsData.Events` is a sixty-four-entry in-memory ring that resets when the daemon restarts, so a restart would re-push everything still in it. The watermark is per device, stored in `devices.json` beside the push token, advanced when a push is accepted by APNs, and consulted before every send. Without it the feature's most visible bug is "lola spammed my phone after I rebuilt it".

**Deep links** go straight to Session detail with the answer card focused. That path is the product; every other push destination is a consolation prize.

No files move, so the Wails `//go:embed frontend/dist` build is untouched and the desktop app does not notice mobile exists. If shared-directory noise becomes real — a hover-only component that is dead on touch, a desktop refactor that breaks a mobile view — promote `lib/` to a workspace package **then**, not pre-emptively.

**"Unmodified" is only true behind a service shim, and the shim is an M1 deliverable.** The real numbers, counted: **28 of the 49 `.svelte` files** under `desktop/frontend/src/lib` (18 of the 36 in `components/`) import `$lib/store.svelte`, `@bindings` or `@wailsio/runtime` — and both flagship reuse examples are among them. `SessionsTable.svelte` imports the store; `LiveTerminal.svelte` imports `Events` from `@wailsio/runtime` **and** `TermService` from `@bindings/desktop`. `store.svelte.ts` itself imports `Events` plus `DaemonService`/`ConfigService`/`TermService`, and registers `Events.On("daemon:sessions" | "daemon:projects" | "daemon:status" | …)`. Aliasing `@bindings` supplies the DTO *types* but not the service call classes those components actually invoke. So `mobile/src/wailsshim/` implements that call surface and an `Events.On` emitter over the native transport, and the claim in the milestone below is "unmodified **behind a service shim**", not "unmodified". One genuine advantage falls out of the same reading and is worth stating: the desktop's `pushLoop` already emits those events on a 2 s cadence, so the shim's event *shape* is defined by working code rather than invented — and it is the natural place for M3's delta subscription to land without any component knowing.

**Permissions and Info.plist keys, because a denied one-shot prompt is unrecoverable in-app.** The macOS side is covered below; the *client* has its own, and iOS 14+ prompts the client for any LAN destination, a QR-supplied raw IP included.

| Key / permission | Needed for | Plugin |
|---|---|---|
| `NSLocalNetworkUsageDescription` (mobile bundle) | any connection to the daemon | `LolaTransport` |
| `NSBonjourServices` | only if `_lola._tcp` is ever queried (M6) | `LolaTransport` |
| `NSCameraUsageDescription` | scanning the pairing QR | a barcode-scanner plugin (candidate: `@capacitor-mlkit/barcode-scanning`) |
| `NSFaceIDUsageDescription` | M4's privileged-action re-auth | `LolaTransport` (the gate is in the plugin, so the prompt is too) |

| Android `POST_NOTIFICATIONS`, `FOREGROUND_SERVICE` | M6 push and an attached terminal | as above |

Plugin availability is exactly the kind of claim this plan verified for its Go dependencies and must verify here too before M1 closes; none of the three named above is load-bearing enough to change the architecture if it has to be replaced, but a missing one is a week nobody budgeted. And "first launch on a device where local network is **denied** shows an actionable explanation rather than a connect error" is in M1's definition of done, because `Network.framework` surfaces that denial as an opaque connection failure and the prompt does not come back.

The Go side adds `internal/pair`, `internal/devices`, `internal/remote`, `internal/panebus`, `internal/push`, `internal/discover`, plus `internal/daemon/remotewire.go` and `internal/daemon/pairwire.go`. Nothing moves.

**The native plugin is the one piece nobody gets for free.** `LolaTransport` is roughly a thousand lines of Swift and a thousand of Kotlin: open a TLS 1.3 connection with a pinned server SPKI and a hardware-backed client identity, run the pairing transcript, hold the capability tier, frame and unframe the envelope, and post decoded frames across the Capacitor bridge. The research found no off-the-shelf Capacitor plugin that does this, and no proposal budgeted it. It is budgeted here, in M1 and M2, and it is the price of taking the security review seriously while keeping the UI in Svelte. The bridge cost is one `postMessage` per keystroke and batched chunks per output flush, which is sub-millisecond in practice and which the daemon's existing 16 ms coalescing already amortises.

**Build.** `npm run dev` in `mobile/` for the browser-hosted UI against a daemon on the same machine; `npx cap sync ios && npx cap run ios` for a device build; the same with `android`. The Go side is unchanged: `make check`.

**Testing.** `internal/pair` and `internal/devices` are pure and are landed **first**, with exhaustive table tests and published test vectors, before a single line of network code exists — a hand-built transcript is exactly the kind of thing that is fine until it silently is not, and there is no second reviewer on this team. The Swift and Kotlin implementations of the same transcript are checked against those vectors in their own unit tests, so a divergence fails a build rather than a pairing. `internal/remote` and `internal/panebus` are tested through their seams and never touch tmux or a socket. The frontend keeps the existing vitest suite plus mobile-specific tests for the accessory bar's byte encodings.

**The plugin needs its own test story, because it holds a security control.** Roughly two thousand lines of Swift and Kotlin are covered today by exactly one thing — the transcript vectors — and the capability tier and the biometric gate both live *there* by deliberate design, which makes them security controls with no named test. So: XCTest and JUnit suites over `LolaTransport` covering, at minimum, **capability enforcement** (a frame the device's tier does not permit is never emitted), **pin mismatch** (a wrong server SPKI fails the connection rather than the proof), the frame codec, reconnect, and `4403`/`4503` handling. One automatable device smoke test (Maestro or XCUITest — scan a fixture QR, land on the sessions list) goes into the CI story so "the app still launches and connects" is not a manual check forever. And the accessory bar's byte encodings are verified **against a live agent** once per milestone during the physical-device pass: a vitest assertion can only prove the code emits what the test expects, never that `\x1b[Z` is what Claude Code actually reads.

**CI impact, and a precondition.** The existing workflow is Go-only: gofmt, vet, build, and `go test` split into race and no-race package sets. There are **35 `.test.ts` files** under `desktop/frontend` — including `LiveTerminal.test.ts` and `Controls.test.ts` — and **none of them run on a pull request today**. Stated precisely, because the accurate version is the more credible one: the vitest suite is genuinely unrun, while the one cross-language mirror that matters most *is* already pinned — `desktop/state_parity_test.go` is a Go test and `go list ./...` includes `desktop`, so it runs on every PR. That parity pin is this plan's own model for keeping a mirror honest; what is missing is everything else. **Adding a cheap `ubuntu-latest` node job running `npm run check && npm run test` in `desktop/frontend` is a precondition of this plan, not a milestone in it**, and must land before the first file is aliased into `mobile/`. A different runner is safe for that job specifically: the existing jobs are on `macos-latest` because the `desktop` *Go* package imports wails/v3, which needs GTK4/WebKitGTK on Linux — the frontend job compiles no Go and has no such constraint, and Linux minutes are 10× cheaper. Beyond that: extend the node job to `mobile/`, and add an `xcodebuild -scheme App CODE_SIGNING_ALLOWED=NO` compile smoke test on the macOS runner — which is 10× billing, so it runs on `main` and on PRs touching `mobile/ios/**` rather than on every push.

**Device days are mandatory and cannot be automated away.** iOS local-network privacy is **not implemented in the Simulator**, so `NSLocalNetworkUsageDescription` and the whole connect path can pass CI and fail on a phone. Budget a physical-device pass per milestone and say so in the milestone's definition of done.

**Distribution** is internal TestFlight only — up to a hundred testers on the same App Store Connect team, no App Review — plus a debug APK. External TestFlight still requires an App Review pass, and a QR-paired LAN-only app has no demo environment to hand a reviewer; if public release is ever wanted, budget a rejection loop with a screen recording and detailed notes. The $99 account is required regardless, because the free seven-day provisioning profile means re-signing weekly.

**How a TestFlight build is actually produced, and how it is versioned, are open** — see Open questions. What the plan can say is the constraint: `release-please-config.json` is a single root package that bumps `desktop/build/config.yml`'s `info.version`, and the mobile app has a marketing version and a build number with no defined relationship to the daemon's tag. Since the envelope's `V` already carries protocol compatibility, the mobile version does **not** need to track the daemon release — but somebody has to say so, and whether the IPA is built by hand on the maintainer's Mac or in `build.yml` behind new App Store Connect API-key secrets (beside the Apple signing secrets already there) is a decision with a maintenance cost attached either way.

**Two macOS-side details that will otherwise cost a debugging session each.** Local network privacy landed in macOS 15 and Apple auto-allows launchd *daemons* and processes started from Terminal — but **not launchd agents**. lola's launchd agent plist must set `AssociatedBundleIdentifiers` or the listener becomes unreachable **with no error at all**, which will read as "mDNS is broken". And the desktop bundle needs `NSLocalNetworkUsageDescription` because a daemon it spawned is attributed to it. There is a **second** silent-denial source with an identical symptom and a different fix: the macOS **application firewall** prompts on first bind, and silently denies for an unsigned binary or one started from Terminal. `internal/doctor` gains a check that dials the listener from a second process and — this is the part that earns its keep — **distinguishes the two**, because "unreachable with no error" is the signature the doctor overlay exists for and telling someone to fix the wrong one wastes the same session twice.

## Milestones

### M1 — The byte pipe

The smallest thing that proves the architecture, and it deliberately proves the *risky* half first. One live agent pane, rendered by xterm.js inside a Capacitor WebView, on a **physical iPhone**, streaming from `internal/panebus` through a raw TLS socket owned by a first-draft `LolaTransport`, with a read-only sessions list beside it.

**Ships:** `internal/panebus` with the `vtterm.Tap` addition, window-size tracking and the resync frame; `protocol.Frame`; a minimal `internal/remote` with the `Handle` seam and the frame codec; `LolaTransport` doing TLS and framing but not yet pairing; the `wailsshim` service/event layer; the Capacitor shell rendering `SessionsTable`, `StatusPill` and `theme.ts` **unmodified behind that shim**, plus `LiveTerminal.svelte` and a first accessory bar.

**Status (2026-08-28).** The daemon half of M1 is in the tree and both builds are green (`make check`, and `go build`/`go vet`/`go test -tags lola_insecure`). **Landed:** `internal/vtterm`'s `Tap`/`WithScreen`/`Screen` additions; `internal/panebus` (one tmux attach per pane, byte fan-out, window-size tracking, the resync frame, a shipped `Fake`); `protocol.Frame` plus the length-prefixed frame codec in `internal/protocol`; `internal/remote` (TLS listener, envelope validation, bounded dispatch, the `Handle` seam, the pane path, the audit line, the device key and the SPKI pin, bind resolution, and the tag-split insecure authorizer); `[remote]` in `internal/config` with README and `config.example.toml` entries; and the daemon wiring in `internal/daemon/remotewire.go` — the `remotePanes` adapter, the session-store identity gate, `startRemote`/`stopRemote`/`reloadRemote`, `Handle` bound to `d.handle`, shutdown ahead of `drainConnWork`, and the `remotelisten.go` / `remotelisten_off.go` tag split that keeps `remote.Listen` out of an untagged binary entirely (verified with `go tool nm`). **Remaining:** every *Definition of done* item below, all of which are measurements against a physical iPhone and none of which the daemon can self-report, plus the first compile of the Swift half — see the client status below. One known daemon-side gap remains: `ResyncPayload` carries no DECCKM/bracketed-paste mode, so a client sends `\x1b[A` where the app expects `\x1bOA` until the agent next emits the sequence. Cursor visibility is no longer among them — `ResyncPayload.cursorHidden` carries it, stated in the negative so an absent field means "visible", which is both the common case and the safe default for a client meeting an older daemon.

**Client status (2026-08-28).** The client half is now in the tree under `mobile/`, unbuilt: no toolchain in this workflow could run `npm install`, Capacitor or Xcode, so nothing here has been compiled for a device and every step is written down in [mobile/README.md](README.md) instead. **Landed:** the Capacitor shell (`package.json`, `vite.config.ts` with the alias table the whole reuse bet rests on, `tsconfig.json` mirroring it, `capacitor.config.ts`, `index.html`, `app.css` importing the desktop's wholesale); `mobile/src/wire` — a hand-maintained mirror of `internal/protocol` with the Go-byte-exact codec, the platform-free `Transport`/`FrameChannel` seams, the request/response correlator and twenty golden vectors in `testdata/frames.json`, which `internal/protocol/goldenvectors_test.go` now reads as well, so `make check` catches a drift between the Go and TypeScript views of the wire; `mobile/src/wailsshim` — the six Wails service namespaces and the event bus reimplemented over the remote protocol, with each method marked forwarded, platform-refused or deliberately absent, plus `ChannelTransport` (correlation, the client-side denial mirror, pane subscriptions, sequence-gap classification) and the poll loop that synthesises `daemon:sessions`/`projects`/`status`/`alive`/`pusherr` from requests, since the protocol has no push; `mobile/plugins/lola-transport` — the Capacitor plugin's TypeScript API and its Swift implementation (NWConnection, TLS with a `sec_protocol_options_set_verify_block` SPKI comparison, the length-prefixed codec, the bearer handshake, batched inbound delivery) with unit tests for the pure half; and the three screens — Connect, a read-only Sessions list reusing `store.svelte.ts`, `theme.ts`, `filters.ts`, `StatusPill`, `PrBadge` and `AgentActivity` unmodified behind the shim, and a Terminal built on xterm.js with pan/pinch, an accessory bar that encodes its own key bytes, and the mid-turn typing friction. **Two deliberate departures from the *Ships* line above.** `SessionsTable` and `LiveTerminal.svelte` are **not** reused: the first is a seven-column table whose narrowest sensible width is roughly 700pt, and the second fits its grid to the container, has no font-size prop and is fed by `TermService` rather than by resync plus pty frames — all three inverted on a phone that must render the developer's full 200-column grid and pan over it. Both were re-implemented on the mobile side (`SessionRow`, `MobileTerminal`) with every CLAUDE.md invariant carried across explicitly; `desktop/frontend` was not edited, and the shim still exposes the surface a reused `LiveTerminal` needs. **Not yet true:** the bearer key is not persisted — the plugin ships no Keychain methods, so it is held in memory for one app run and the connect screen says so; the Swift tests have never been executed; and `Button.svelte` still has no 44pt touch rung, so `TouchButton` wraps it and the size ladder is forked across two files until someone adds one literal to its `SIZES` map.

**Review pass (2026-08-28).** Two independent reviews of the daemon half landed six defects worth naming, all fixed with regression tests: `panebus.Sub.offer` sent on a channel a concurrent `Close` could close, and the recovered panic stranded the bus teardown so `Registry.Close` — and therefore `stopRemote` — hung forever while the tmux child leaked; `bus.repair` did not flush before taking its screen, so a recovered subscriber was re-sent bytes its own repairing resync already showed; `conn.pump` announced a pane's death before dropping the subscription, so a client's reply raced a write onto a dead pane; `maxConnections` counted only peers that had finished a handshake, so unauthenticated sockets were unbounded; `remote.Server.Close` transitively waited for `pollOnce`, which runs on `context.WithoutCancel`, putting an unbounded wait inside the step that exists to remove one; and the pane-name shape gate refused any project whose `Name` carries an upper-case letter, which `config` explicitly still allows. `internal/vtterm` also stopped calling the vendored emulator's racy `Close`, so `internal/tui` and `internal/vtterm` no longer need CI's `-race` exclusion and no longer have one.

**Explicitly deferred:** all cryptography. Authentication in M1 is a hard-coded key read from `LOLA_REMOTE_INSECURE_KEY`, the listener refuses to start without that environment variable *and* logs a warning on every accept. "Deleted, not disabled, in M2" is a promise enforced by memory, so it is enforced by the compiler instead: the whole path sits behind a **`//go:build lola_insecure` tag**, so a release binary cannot contain it, and while that tag is active `bind` is forced to `localhost` regardless of config — M1's stated goal is one phone on the same WiFi, which a localhost bind plus an SSH forward satisfies without a shared bearer secret ever reaching a network interface.

**Definition of done**, and each is measurable rather than felt:

- On a physical iPhone, a real Claude Code session's composer, its `▔` modal overlay rule and its live status line (`✻ Harmonizing… (5m 58s · ↓ 17.9k tokens)`) are readable, judged by the maintainer against a screenshot of the same pane on the Mac.
- Escape, Ctrl-C, Shift-Tab, arrows into an AskUserQuestion picker, and Shift+Enter all work, verified **against a live agent**, not against a test double.
- The desktop's 200-column view is provably unchanged while the phone is attached, verified with **three concurrent clients** (desktop, phone, a stray CLI `tmux attach`).
- **The desktop resizes its window mid-stream and the phone receives a fresh, correct resync frame** — the cheap test that catches a stale shadow emulator before it gets misdiagnosed.
- Scroll moves the agent's own transcript.
- An idle pane costs **under 1 KB/minute measured at the listener over five minutes** with the agent parked at its prompt.
- First launch on a device where **local network is denied** shows an actionable explanation, not a connect error.

**This milestone can kill the plan, and that is its job.** If xterm.js in WKWebView cannot render an agent pane legibly and take keyboard input reliably, the correct response is to swap the terminal screen — and only that screen — for a SwiftTerm-backed native view behind the same `Transport` interface, or in the last resort a `vtterm`-rendered cell grid through the existing `ansi.ts`. Everything else in the plan survives that swap unchanged. Finding this out in month one is worth more than any other property of the sequencing.

### M2 — Pairing, devices, capabilities

**Ships:** `internal/pair` and `internal/devices` as pure, exhaustively table-tested packages with published test vectors, landed *before* the network code that uses them; mutual TLS with full-length SPKI pinning in both directions; the full transcript, proofs and three-emoji SAS; `pairBegin`/`pairStatus`/`pairConfirm`/`devices`/`revokeDevice` on the socket; the desktop's "+ Connect app" button, 1-of-3 confirmation and device list; `lola pair`, `lola devices`, `lola revoke`; the per-device address book; the capability tiers as a closed allowlist with the per-command `Request` rebuild, the frame-type gating and the parity test over `d.handle`'s `switch`; the audit line; per-device cost-based rate limiting; the M1 insecure path deleted along with its build tag.

**Deferred:** push, deltas, mDNS, Android.

**Done when:** a phone **with no keychain entry** (not a factory reset — that is not a repeatable gate) pairs from a QR in under thirty seconds; both screens show the same three emoji and the desktop's confirmation is a selection among three; a deliberately mismatched pin fails the proof rather than the pin check; a wrong proof does *not* burn the window but a third one does, with a message naming the real cause; `lola revoke` closes a live connection within a second and the phone returns to the pairing screen while an **unreachable** daemon does not; a device with only `read` is refused `answer` **and** refused a pane subscription at the boundary; a `kill` frame carrying `force: true`, `Hook` and `Event` reaches `d.handle` with only the fields `kill` reads; a `hookEvent` frame is refused before `d.handle`; a new `case` added to `d.handle` fails the parity test; and the Swift and Kotlin transcript implementations pass the Go test vectors.

### M3 — The product surface

**Ships:** Needs You as the home screen, `SortRank`-ordered, with the five `KanbanColumns()` chips; Session detail with the status header, PR card and — the point of the whole exercise — the **answer card** built from `PaneData.choices`, gated on `inputReason`; the Feed from the event ring filtered by `Notable`; the terminal promoted to a full screen with a tab bar over agent, `-shell-N`, `-dev-N` and `-review`; `subscribe` frames with a cursor so the daemon sends deltas instead of the phone re-pulling 12.8 KB; offline rendering of the last snapshot behind an "as of 12m ago" banner with every mutating control disabled.

One small protocol addition belongs here: `protocol.Event` carries only `Ago`, a string formatted daemon-side against request time, while `SessionInfo` deliberately carries raw `time.Time` stamps "so a client can render a live 'ago' between refreshes". Served over a delta subscription, `Ago` freezes at delivery or forces a full re-pull, which defeats the delta. So `Event` gains `At time.Time \`json:"at,omitzero"\`` — a wire-compatible addition in the same shape as the axis freshness stamps, which the TUI and desktop may adopt or ignore.

**Deferred:** everything in the `control` and `destructive` tiers.

**Done when:** an agent parked on a yes/no is answered from a locked-then-unlocked phone in three taps; the sessions view costs **under 2 KB/minute at rest** over five minutes with no session changing state; a push tapped with **no route to the daemon** renders the cached snapshot behind the staleness banner and names the reason; and a **daemon restart** is survived without a blank screen — which needs saying explicitly, because the resume mechanism (`Seq`, the per-pane ring, the resync frame) is specified for a *reconnect*, and after a restart the ring and the bus are gone while the tmux sessions are not. The client re-subscribes, `Seq` restarts from zero, and a fresh `resync` frame rebuilt from a newly attached shadow emulator is what it receives.

### M4 — Control

**Ships:** the `control` and `destructive` tiers with confirmation sheets that name what will happen — the dev toggle names the session whose servers it will stop, `devFreePort` shows the process, directory and whether it is ours, `switchAgent` says the turn restarts, `kill` says the worktree goes. Review, CodeRabbit, resolve-conflicts, revive, poll enable/disable/once, the ticket picker and manual branch/PR open. Biometric re-authentication **enforced in `LolaTransport`** (60 s validity, one action per success) in front of `destructive` and `switchAgent`. Projects as read-only cards.

**Deferred:** nothing new; this is the completion of the command surface minus the permanent denials.

**Done when:** every action the desktop's context menu offers is reachable except the commands denied in code, each destructive one confirms once through the shared confirm store, a `destructive` frame emitted without a fresh biometric success is refused **by the plugin** (verified with the WebView instructed to skip the prompt), and the audit log names the device for each — with no payload in the line.

### M5 — Push

**Ships (iOS only — there is no Android push, per *Settled since drafting* (5)):** `internal/push` with APNs over HTTP/2 and a `.p8`; a `pushChannel` inside `internal/notify` holding a `push.Sender` seam that enqueues rather than blocks; the three priority tiers with per-device preferences; **opaque per-device handles** with content fetched over the paired channel after unlock; the persistent per-device watermark; the authenticated `updatePushToken` frame; deep links into the answer card.

**Deferred:** nothing push-related is deferred — there is no Android push to defer. Android simply has no wake path (*Settled since drafting* (5)).

**Done when:** a phone locked in a pocket buzzes **within ten seconds** of an agent parking on a question; the notification opens directly onto the focused answer card when a route exists and onto the cached snapshot with a named reason when it does not; a daemon restart does not re-push the event ring; `notify.Notify` returns without waiting on APNs (asserted with a blocked sender); and **a Go test over the marshalled payload asserts that no session id, Linear identifier, project name or session title appears in it** — that one is trivially automatable and is the only security-relevant done-when here that was previously left as an observation.

### M6 — Android, discovery, hardening, off-LAN

**Ships:** the Android target from the same Capacitor project with `LolaTransport` in Kotlin against Keystore/StrongBox; the `internal/doctor` local-network-versus-firewall denial check; `AssociatedBundleIdentifiers` on the launchd agent plist and `NSLocalNetworkUsageDescription` on the desktop bundle; README and `config.example.toml` documenting `[remote]` including the plain-language statement of what enabling it grants and the sentence about what `bind = "lan"` means on a laptop.

**The mDNS advertisement says as little as possible** — *shipped, ahead of this milestone; the rule below is what it obeys.* `_lola._tcp` on a shared network announces "this machine runs autonomous coding agents and accepts remote control" to every peer on it. So the TXT record carries the **protocol version and nothing else** — no SPKI prefix, no device ids, no hostname, no session or project names — because an SPKI prefix or a hostname in a TXT record is a stable cross-network correlator for the operator's laptop. The instance name is likewise not derived from anything identifying: it is the constant `lola`, and mDNS appends " (2)" itself when two daemons share a network. `advertise = false` stays the default and `config.example.toml` calls turning it on a **disclosure**, not a convenience.

The first implementation violated all three halves of that paragraph — it published the SPKI pin in the TXT record, named the instance `lola on <hostname>`, and advertised unconditionally with no config key — which is worth recording because each looked locally reasonable: the pin lets a browsing phone drop an impostor without opening a socket, and a hostname makes a picker readable. Neither survives the correlator argument, and the phone needs neither: it opens one pinned TLS handshake, which is what decided trust in the first place, and it walks candidates rather than showing a picker.

**Android's background story, which iOS's has no equivalent of and which is not optional.** The iOS analysis (suspension in ~30 s, VoIP sockets gone since iOS 13) concludes that push is mandatory; Android's constraints are different and worse in one respect. Doze, App Standby and the aggressive OEM process killers on Xiaomi, Samsung and OnePlus will terminate a backgrounded long-lived socket and, on some OEMs, the process. So: an **attached terminal runs under a foreground service with a persistent notification** (with the Play policy consequence that entails, which matters only if this is ever distributed publicly), `REQUEST_IGNORE_BATTERY_OPTIMIZATIONS` is prompted for once with an explanation, and **there is no wake path at all**, because FCM is out (*Settled since drafting* (5)). State the resulting shape plainly rather than discovering it as a bug: Android is useful while the app is open and the phone is on the daemon's network, the foreground service keeps an attached terminal alive while the app is backgrounded, and a phone in a pocket learns nothing until it is picked up. Everything ranked #1–#3 under *What the phone is for* is therefore an iOS-only property today. Revisiting means accepting FCM.

**Optional and explicitly opt-in:** `tailscale.com/tsnet` behind `[remote].mode = "tailnet"`, which embeds a userspace Tailscale node in the daemon — no root, no `tailscaled`, no system configuration — and which would remove the need for discovery entirely since MagicDNS names replace mDNS. It is a heavy dependency and an authentication model outside lola's control, so it is a mode, never the default. It is also the only thing in this plan that makes the "answer it from a train" story literally true, which is worth weighing against its position as an option. **No relay is built**, ever: a relay makes this project responsible for uptime and introduces a trust boundary it does not need.

**Done when:** an Android phone pairs and answers an agent; an Android phone with the screen off for thirty minutes still receives a push and reconnects on tap; **a network with client isolation still pairs from the QR** (verified on an AP with client isolation explicitly enabled, or a guest SSID that has it on by default — named, because "a network with client isolation" is not a test setup); and a launchd-agent daemon on macOS 15 either works or says which of the two denials it hit.

## Open questions

These need a human decision and are not the plan's to make.

**Can xterm.js in WKWebView actually do this?** The single existential bet. Nobody has rendered a Claude Code pane in a WebView on a phone at fifty-five columns. M1 answers it; the escape ladder is named; but if the answer is no, the terminal screen becomes native and the plugin grows by a few thousand lines.

**Does an SE-backed `SecIdentity` work for mutual TLS through Network.framework?** It should — that is what `sec_identity_create` is for — but the research did not confirm it, and the equivalent question for OkHttp with a StrongBox key is equally unconfirmed. If either fails, TLS degrades to server-auth-only on that platform. The transcript binding survives that (the phone's identity component becomes its enrolled public key rather than a certificate SPKI, and a relay still mismatches), but the pre-authentication surface grows from the TLS stack to the WebSocket upgrade and the JSON parser. Spike this in M1.

**Should remote `openURL` exist?** The plan moved it out of the default tier into `control` and restricted it to URLs the daemon itself surfaced, because in the default tier it is a remote party opening arbitrary https URLs in a browser logged into GitHub, Linear and the corporate SSO. The remaining question is whether the "put this on my Mac's screen" action is worth having at all once the phone opens links locally.

**Should the pairing window be shorter than 90 seconds?** It was chosen as a guess. The observed-QR attack's exposure is bounded by it, and the scan-to-confirm path has not been measured on a device.

**Should the desktop app move to `internal/panebus` too?** Today it drives `tmux -L lola` directly. Two attach paths is two places for the alternate-screen and copy-mode invariants to drift — and now for the window-size and shadow-emulator invariants too. Consolidating is a real cleanup and a real regression risk on a surface that currently works.

**How are TestFlight builds produced, and does the mobile version track the daemon's?** By hand on the maintainer's Mac, or in `build.yml` behind new App Store Connect API-key secrets beside the Apple signing ones already there. And `release-please-config.json` is a single root package bumping `desktop/build/config.yml`'s `info.version`, with no defined relationship to a mobile marketing version and build number. The envelope's `V` means the app *need not* track the daemon release; somebody still has to say so.

**Bundle identifier, App Store Connect team, and who holds the $99 account.** The desktop bundle is `dev.sushi.lola.desktop` and must not change. `dev.sushi.lola.mobile` is assumed throughout but is not decided, and the mobile app is a separate identifier with separate TCC grants and a separate provisioning profile.

**What licence does the mobile app ship under, and does it matter?** The plan avoids GPL-encumbered terminal code specifically so this stays open, but nobody has stated the intended answer.

## Rejected alternatives

**The Wails 3 mobile target already scaffolded in this repository.** It has to be named, because it is sitting in this tree and it is the option that shares the most code of anything considered. `desktop/build/ios/` carries `project.pbxproj`, `Info.plist`, `entitlements.plist`, `main_ios.go`, `app_options_ios.go`, `LaunchScreen.storyboard` and a `Taskfile.yml` with `ios:package`, `ios:package:ipa` and `ios:xcode`; `desktop/build/android/` has gradle, `main_android.go` and a wrapper; `.github/workflows/ci.yml` excludes `desktop/build/**` from the Go steps *specifically because of them*. Taking that route would share the same Go module, the same six Wails services, the same `@bindings` — and therefore all twenty-eight Wails-coupled components including `SessionsTable` and `LiveTerminal`, which is to say it dissolves the shim problem above outright rather than solving it. It is rejected on maturity, not on architecture: the module is pinned at `v3.0.0-alpha2.117`, its mobile support is alpha, and the whole plan's dependency ethos is that a solo maintainer does not become the owner of someone else's unfinished platform layer. Note that the daemon-not-desktop binding survives either choice — a Wails mobile app would still be a socket/WSS client of `lola run` — so this is a UI-host decision and nothing in the transport, pairing or capability design changes if it is revisited when Wails 3 mobile leaves alpha.

**Flutter with xterm.dart.** The strongest rival, and it loses on one fact: `xterm.dart` last released in February 2024 and has had zero commits in twelve months against 107 open issues, with the fixes that matter here — alternate-screen scroll, SGR mouse-wheel codes, DECSTBM, synchronized output — sitting in unmerged pull requests. A maintained fork exists and drives a real app, so vendoring it is not absurd; but vendoring a VT parser makes a single maintainer the permanent owner of an emulator, and this repository's maintainer already owns roughly seven hundred lines of invariants. The proposal's own stated fallback was to host xterm.js in a WebView — that is, to become this plan, after first paying for Dart, a re-derived theme layer and a second parity mirror. When a plan's escape hatch is a competing plan, the competing plan should have been the plan.

**Native SwiftUI with SwiftTerm, and Compose later.** SwiftTerm is the best terminal engine in this comparison by a wide margin — 474 commits in the last year, MIT, TrueColor, bidi, OSC 8, an optional Metal renderer — and a real `inputAccessoryView` on a real `UIView` is a keyboard stack no WebView can match. It loses on arithmetic. It asks one person to learn Swift and Kotlin, maintain an Xcode project by hand, build and own a `go/packages` codegen tool emitting both Swift `Codable` and Kotlin `@Serializable`, and keep a third and fourth regex mirror of `internal/state` alive beside the existing `theme.ts` one. And it concedes the argument on Android: there is no maintained permissively-licensed Android terminal view (Termux's is GPL-3.0), so its own plan puts xterm.js in a WebView there. It pays native's full price and gets native's benefit on half the platforms the goal requires. SwiftTerm remains the named escape hatch for the iOS terminal screen if M1 fails, and it is the right escape hatch precisely because the terminal sits behind one interface.

**gomobile as a shared Go core.** A trap, and checkably so. `gobind` binds signed integers, floats, string, bool, `[]byte`, functions, interfaces, and structs whose exported fields are all of those — no slices, no maps, no `time.Time`, no struct pointers. `protocol.go` alone declares more than twenty offending fields: `SessionsData.Sessions []SessionInfo`, four `time.Time` timestamps on `SessionInfo`, `DevCommands []string`, `DevURLs []string`, `DevClash *DevClashInfo`, and `map[string]int` guards on the session model. The only API that actually binds is `Send(string) (string, error)`, which is JSON across an FFI boundary — exactly what the newline-delimited-JSON socket already provides without a toolchain, a Go runtime and a second garbage collector in-process, an XCFramework plus an `.aar` across several ABIs, and a hand-written FFI layer per framework anyway. `golang.org/x/mobile` still opens its README with "experimental, use at your own risk", and `gobind` states that a panic crossing the language boundary exits the program — an uncatchable app crash. What is genuinely worth sharing is about three hundred and twenty lines of pure tables, and the existing eighty-six-line parity test is the right tool for that.

**React Native or Expo.** No native terminal exists there either, so the terminal is xterm.js in `react-native-webview` — this plan's terminal with React's complexity added and Svelte's reuse removed. Everything else it offers, Capacitor offers with the existing frontend intact.

**Kotlin Multiplatform with Compose Multiplatform.** Disqualified outright: a search for a Compose Multiplatform terminal emulator returns nothing, so the app's entire budget would go to writing a VT parser and renderer from scratch, on a UI toolkit still fixing text-field divergence and iOS crashes.

**QUIC or HTTP/3.** Better on paper for roaming — connection migration, 0-RTT, no head-of-line blocking across streams — and rejected because iOS suspends UDP sockets aggressively in the background, so the connection has to be re-established on wake anyway. That is the whole advantage gone, in exchange for a heavy dependency. Multiple WebSocket connections (control plus one per pane) achieve the same stream independence over TCP.

**Noise over raw TCP instead of TLS 1.3.** A fine protocol whose Go implementation, `flynn/noise`, has been stale since early 2024, and which duplicates what `crypto/tls` already provides — authenticated key exchange, forward secrecy, transcript hashing. TLS gets us ALPN, a well-audited stdlib implementation, and a path to reverse proxies later. The one thing Noise would have given for free is a handshake hash to bind the SAS to; the transcript construction above provides that explicitly.

**A PAKE with a short typed code.** SPAKE2 or CPace with a six-digit code is the right answer when the out-of-band channel is a human reading numbers aloud. It is the wrong answer when the channel is a QR code that can carry 128 bits at no cost. It is doubly wrong here because there is no credible maintained Go PAKE — every candidate found is a sub-thirty-star project, and a PAKE with a missing point validation fails silently rather than loudly. If the QR is ever replaced by a typed code, this decision must be revisited together with the emoji count; they are one decision.

**A relay or cloud rendezvous service for off-LAN access.** Rejected permanently. A relay makes this project responsible for uptime, for a new trust boundary, and for someone else's data in transit. `tsnet` is the opt-in answer for people who want off-LAN, precisely because it moves all three of those responsibilities to a party that already has them.

**A `capture-pane`-polling terminal instead of a byte stream.** Sixty lines with ANSI is four to eight kilobytes per poll; at the desktop's 1.4-second cadence that is roughly five kilobytes per second per pane **even when nothing is happening**, which is worse than a byte stream at rest and much worse on cellular. And `capture-pane -p -e` carries no cursor position and no cursor shape, so you cannot see where the caret is — which is exactly what you need in order to answer a prompt. Snapshots stay for the multi-pane overview, where many panes at low fidelity in one round trip is the right protocol.

**Putting `protocol.Request` bare on the wire.** It has no identity field, no version field, no correlation id and no frame type, and `handleConn` is strictly serial per connection so a five-minute `openTicket` would block every subsequent request. Adding those fields to `Request` would pollute the local socket path with concepts it does not have. The envelope wraps; the payload does not change.

**Porting the terminal grid, the kanban board, or the config forms.** Nine `capture-pane` tiles at six points is unreadable at 390 logical pixels. Five horizontally-swiped kanban columns is worse than the five filter chips that already exist. The project form is twelve fields over an inheritance bitmap whose zero value means "fully explicit", plus a fail-closed layout permutation and a local folder picker — none of which is a phone job, and none of which is even on the socket.
